# @blotch/angular-lynx-e2e

End-to-end tests that install and run AngularLynx the way a user does. They catch broken releases before users do: 22.2.0 and 22.2.1 passed every unit test and still couldn't produce a working app. Why it works the way it does is in [`CLAUDE.md`](CLAUDE.md).

## Run it

```sh
npx playwright install chromium        # Once
npm run e2e                            # From the repo root: builds the packages, then layers 1-3
npm run e2e -- --keep                  # Keep the generated app and print its path
npm run e2e -- --layers 1              # Package checks only (seconds)
npm run e2e -- --pm pnpm --angular next
npm run e2e -- --angular lowest        # An app on exactly the lowest Angular the peers allow
npm run e2e -- --tailwind-version 3    # An app on Tailwind 3 and Lynx's preset (the default is 4)
npm run e2e -- --registry public       # Test what is on npm right now
npm run e2e -- --ios                   # Also run on the iOS Simulator (needs Xcode and Maestro, below)
npm run e2e -- --ios --shell           # ...testing the app's own build from `ng build --platform ios`
npm run e2e -- --ios --shell --explorer  # ...testing both, as CI does
npm run e2e -- --help                  # Every option
```

`npm run e2e` from the repo root builds the publishable packages first. Running `npm run e2e -w packages/e2e` skips that, so it tests whatever is already built.

For `--ios`, install [Maestro](https://maestro.mobile.dev) at the version CI uses (`MAESTRO_VERSION` in `.github/workflows/e2e.yml`):

```sh
curl -fsSL https://get.maestro.mobile.dev | MAESTRO_VERSION=2.10.0 bash
```

The iOS run creates and reuses its own simulator, "AngularLynx E2E", so your own simulators stay untouched. To rerun only the native checks against an app you kept with `--keep`:

```sh
node packages/e2e/src/native/run-native.ts --platform ios --dist <app>/dist
```

Add `--app <app>` instead of `--dist` to test the app's own binary from `ng build --platform` rather than Lynx Explorer (the "shell" mode; `--app` builds it, `--prebuilt` uses the one already in `<app>/dist/<platform>`, and `--native <dir>` builds it from `<app>/dist` with an unpacked `@blotch/angular-lynx-native`, for an app without `node_modules`). Add `--explorer` too to test both, one after the other on the same device; a failure in one still lets the other run. iOS shells need Lynx's XCFrameworks: see [`packages/native/README.md`](../native/README.md#lynx-for-ios) for `ANGULAR_LYNX_IOS_FRAMEWORKS`.

```sh
node packages/e2e/src/native/run-native.ts --platform android --app <app>
```

Android has no `npm run e2e` flag: boot an emulator first (CI uses API 34 with Google APIs; on Apple silicon, the `arm64-v8a` image), put `adb` on your `PATH`, then run the same command with `--platform android`.

In CI, Layer 6 tests both hosts on both platforms. The Linux `build-app` job scaffolds the app, builds its APK (`--build-native android`) and hands the app folder (`--export-app`) to the `android` job, which runs `run-native.ts --app <app> --prebuilt --explorer` on the emulator. The `ios` job, on GitHub's `xcode-27` image, starts with the run so the simulator boots while `build-app` works, then waits for the same app folder. The shell can only be built on macOS, so it runs `run-native.ts --app <app> --native <dir>` (adding `--explorer` everywhere but pull requests), where `<dir>` is the unpacked `@blotch/angular-lynx-native` tarball. That builds the shell from the app's bundle the way `ng build --platform ios` does, without installing the app on the Mac (building for iOS, the native builder loads only Node's built-ins: its one dependency, `pngjs`, which makes the Android icons and the splash images, loads only when an Android build or a `splash.image` uses it, and the E2E app has no `splash`). The nightly macOS `fresh-app` job still installs and builds the app on a Mac.

The flows run a shell with everything in it, since the app has a fixture for every feature. Most apps get a shell with code left out: no canvas at all, or a canvas without WebGL and ANGLE for one that draws only in 2D (`leaveOut` in `packages/native`, from the `.angular-lynx-native.json` the build plugin writes), and no barcode scanner without angular.json's `permissions.camera`, which the harness gives the app (`addCameraPermission` in `src/scaffold.ts`). The `no-canvas` variant also drops the camera permission. Only the compiler and the linker see everything those projects still name, so `src/native/compile-features.ts` builds the app's shell once for each, without running it: it copies the app's `dist/`, rewrites the features file, builds with the tested native builder, and checks the generated project left the files out. Each variant also builds without angular.json's `storeReview`, `calendar` and `signInWithApple`, which the E2E app sets, so the shells are compiled once without the store review and calendar modules and their registration, and the iOS shell without the Sign in with Apple module and its entitlement, too. The `no-canvas` variant also builds without `permissions.biometrics` and angular.json's `filePicker`, which the E2E app sets, so the shells are compiled once without those modules and their registration too. The `ios` job runs it after the flows, and the `android-features` job after `build-app`, with the builder installed from the tarball (an Android build needs `pngjs`). Locally, with a built app (node_modules isn't needed):

```sh
node packages/e2e/src/native/compile-features.ts --platform ios --app <app> --native packages/native
```

## Debug a failure

- **Read the last `✗` line.** Every check says what went wrong and where to look.
- **Look in `artifacts/`** (native runs add `<platform>-commands.log`, `<platform>-requests.log` with every bundle Explorer fetched, the app's log per host (`ios-shell.log`, `ios-explorer.log`, `android-<host>-logcat.log`), and in `<platform>-<host>/` Maestro's report, its log and each flow's screenshots, plus `hung-<n>.log` and `hung-<n>.png` if a session hung) (in CI, the `e2e-artifacts-*` workflow artifacts): `commands.log` has every command's output, `verdaccio.log` the registry's, `app/` the generated app without `node_modules`, `npm-logs/` npm's debug logs, and `playwright/` screenshots and traces.
- **Rerun with `--keep`**, then `cd` into the printed path and run `npm run build` or `npm start` by hand.
- **Open a Playwright trace** with `npx playwright show-trace artifacts/playwright/<test>/trace.zip`.

## Things to know

- **The generated app lives in a temporary folder, never in the repo.** Inside the monorepo, Node would resolve missing dependencies from its `node_modules` and hide them.
- **`@blotch/*` and `create-angular-lynx` never come from the public registry** in a local run. Verdaccio doesn't proxy them, so a broken local package can't be swapped for a published one.
- **Verdaccio's storage is cached** in `node_modules/.cache/angular-lynx-e2e/verdaccio` (or `--storage <dir>`), so third-party packages only download once.
- **Verdaccio needs Node 24 or later.** To test an app on an older Node, run the harness on that Node and set `E2E_VERDACCIO_NODE` to the binary of a Node 24 or later for Verdaccio, as CI's Node 22 job does with Node 26.
- **The packages under test come from [`packages/release`](../release/README.md)'s publish list.** A new public package must be added there or marked `"private": true`, or Layer 1 fails.
- **Lynx Explorer is pinned** in `src/native/explorer.ts` with its SHA-256. Bump it together with the Lynx toolchain.
- **Each host's flows run in one Maestro session**, so Maestro starts its driver once per host rather than once per flow. Every flow still opens the app with `native/open-app.yaml`, whose `launchApp` stops it first. A session that finishes no flow for 7 minutes (the driver's 3 to start, and 4 for a flow) is stopped, with a screenshot and the end of Maestro's log saved, and the flows it didn't finish run once more in a new session.
- **The photo `photo.yaml` picks goes into the library before the flows run** (`src/native/library-photo.ts`). On CI's iOS runners the first `xcrun simctl addmedia` often hangs for minutes (#624), so the `--prepare` step that starts the boot also starts a background job, which outlives it, to add the photo once the boot ends. Layer 6 waits for that job, and adds the photo itself when there's none (a local run) or it failed; its log is `ios-photo.log` in the prepare step's artifacts. The flow closes and reopens a picker that shows no photo in 30 seconds, which finds a photo the library got late.
- **A flow the simulator held up runs once more.** On GitHub's macOS runners, the simulator sometimes takes a minute or two to start one of WebKit's processes (issue #633), and the web view loads nothing until then. When `webview.yaml` fails and the app's log shows a WebKit process took over 30 seconds to start, it runs again in a new Maestro session, and fails the run only if it fails again. The photo picker's process stalls the same way (issue #672), leaving PHPickerViewController on "Loading...", so `photo.yaml` runs again when the app's log shows that process took over 30 seconds to start, or still hadn't when the session ended. So does the Metal compiler (issue #890): the first WebGL context after the simulator boots has ANGLE compile its shaders through `MTLCompilerService`, which the simulator sometimes never starts for the app, and ANGLE waits for it on the engine thread, so the canvas page shows none of its results and the app answers no tap. Every flow that opens the canvas page runs again when the app asked for a compile while that flow ran (its time comes from Maestro's `commands.json`) and the compiler hadn't begun it 10 seconds later (the iOS log stream takes in the compiler's lines about the app for this). A flow opts in with `deviceFault` in `src/native/maestro.ts`.

- **Flows that failed in a session where Maestro lost the device run once more, on a restarted simulator.** When Maestro reports `Device became unreachable` (its XCTest driver stopped answering), every flow that failed in that session runs again in a new one, after the harness restarts the iOS Simulator, and fails the run only if it fails again. On one PR's run (issue #862) the app the simulator launched for the first flow sat on a blank screen without logging a line, the driver then couldn't stop it, and all 18 flows failed. Maestro's result lines give no reason for these failures, so the harness reads them from its JUnit report.
- **On Android, another app's "isn't responding" dialog is closed** while the flows run (`src/native/anr-dialogs.ts`). Pixel Launcher can hang as the emulator boots, and its dialog stays over the app, which Maestro then can't see, so every flow fails. The harness force-stops the hung app, as the dialog's "Close app" does, and says so in the log. The app's own dialog stays up: that hang is a failure.
- **The counter fixture loads `fixtures/http-data.json` from `http://127.0.0.1:3210`** through `HttpClient` and `httpResource`, and posts JSON to `/e2e-echo` there, which answers with the `Content-Type` headers the request arrived with and the body's size in bytes (the photo fixture uploads its picked `Blob` there). Layer 3 serves both next to the render server, and Layer 6 from the server that also serves Explorer's bundle, for both hosts. The URLs are absolute because Lynx has no page URL to resolve a relative one against.
- **Native flows can only find elements that aren't flattened.** On Android, Lynx draws most elements into their parent without a View of their own, and Lynx Explorer only builds an accessibility tree for them while TalkBack is on. So every element a flow taps or checks sets `flatten` to false (see `fixtures/counter.ts`), which gives it a View carrying its label or text. iOS doesn't need it, but works the same with it.
- **Known failures are marked, not skipped.** A check for a known bug uses `test.fail()` (or a native flow's `knownFailure`) and names the GitHub issue that tracks the bug, so it turns red when the bug is fixed.
