# @blotch/angular-lynx-native

Builds AngularLynx apps into iOS and Android binaries. You don't call it directly: `ng build --platform ios|android|all` (the `@blotch/angular-lynx-build:application` builder) loads it after building the Lynx bundle. It's a dependency of [`@blotch/angular-lynx-build`](../build), which `ng add @blotch/angular-lynx` installs.

User documentation: [Publishing your App](../website/docs/guide/building-for-production.mdx). The design and its reasoning: [`investigations/native-app-builds.md`](../../investigations/native-app-builds.md).

## What it does

1. **Generates** the native project from `templates/ios` or `templates/android` into the project's folder in Angular's build cache (`.angular/cache/<Angular version>/<project>/lynx-native/<platform>`, which `ng new` already gitignores and `ng cache clean` clears), writing the app options from `angular.json` into the few files the templates mark for it. It regenerates only when a hash of its inputs changes (this package's version, the template, the options, the icon and splash images), so Xcode and Gradle keep their incremental state.
2. **Copies** `dist/` (without the web bundle) into the project.
3. **Builds** it with `xcodebuild` or Gradle and copies the binaries to `dist/<platform>/`.
4. **Runs** it, with `--run` (`src/ios/run.ts`, `src/android/run.ts`): picks a simulator, emulator or phone (`--device`, else a running one, else the newest iPhone simulator or the first AVD) and starts it before step 3, so it boots while the app compiles; then installs the app and opens it. iOS uses `simctl` and shows the simulator in DeviceHub (`devices://device/open?id=<UDID>`) or, before Xcode 27.1, the Simulator app. When `--device` names a paired iPhone (`src/ios/iphone.ts`, found with `devicectl list devices`), step 3 builds a development-signed `-sdk iphoneos` app for it instead (`ios.teamId`, `-allowProvisioningUpdates`), and `devicectl` installs and opens it. Android uses the SDK's `adb` and `emulator` and opens the launcher activity by component.

5. **Develops** in it, for `ng serve --platform ios|android` (`devServer` in `buildNativeApp`): generates the project into `lynx-native/<platform>-dev` without a bundle, builds Xcode's Debug configuration (for the picked simulator alone, into its own derived data) or Android's debug build type (`:app:assembleDebug`, the debug key), and opens it with the dev server's URL: a `-AngularLynxDevServer <url>` launch argument on iOS (`simctl launch`, `devicectl ... process launch`), `--es AngularLynxDevServer http://localhost:<port>/main.lynx.bundle` and `--es AngularLynxDevServerOrigin <the address the bundle was built with>` on Android, after `adb reverse tcp:<port> tcp:<port>`. A stamp next to the app (`src/dev-build.ts`) records the project's input hash and the device; when both match, the next `ng serve --platform` reinstalls the app without running Xcode or Gradle. An ejected project is always built, and one ejected before this existed (no `DevServer.swift` / `DevServer.kt`) fails with a message to eject again.

An ejected project (`ios/` or `android/` with a `.angular-lynx-ejected` marker, written by `ng generate @blotch/angular-lynx:eject`) is built as it is and never regenerated.

## The shells

Both are one full-screen `LynxView` running `main.lynx.bundle`; Angular Router does all navigation inside it. Bundles and assets load from inside the app, so RSpeedy's default asset prefix (`/static/...`) works with no configuration. The `LynxView` fills the screen, under the status bar and the home indicator (`"edgeToEdge": false` in angular.json puts it inside the safe area instead). Lynx's own CSS `env(safe-area-inset-*)` is 0 there: Android never sets it, and the iOS shell creates its `LynxView` before the window is key, where Lynx reads it. The runtime gives every `env(safe-area-inset-*)` the insets the shell sends instead (see `safe-area-insets.ts` in the runtime), so they follow rotation. On Android the activity still pads the page for the keyboard, and the bottom inset is 0 while it's open. An `<overlay>` fills the screen too, so a bottom sheet covers the page down to the screen's edge and pads its content by the insets: on Android XElement's overlay window stops above the navigation bar, so the shell registers its own `overlay` behavior, `EdgeToEdgeOverlay.kt`, whose window draws under every bar, as the activity's does.

Both run Lynx's engine thread, where the main thread's JavaScript, and so the whole Angular app, runs with layout and Lynx's animator, off the platform's UI thread: Lynx's `MostOnTASM` thread strategy (`setThreadStrategyForRender(.mostOnTASM)`, `setThreadStrategyForRendering(ThreadStrategyForRendering.MOST_ON_TASM)`), where Lynx's default, and Lynx Explorer's, is `AllOnUI`. So change detection, a screen being built or a busy event handler doesn't freeze what UIKit and Android run themselves: a scroll view's momentum, typing in a text field, a web view. The cost is that the element tree reaches the screen a step later, after the flush crosses to the UI thread, and UI methods with it: the build plugin turns on Lynx's pending invokes (`enableElementInvokeUIMethodPendingTask`), which send a method after the flush that makes the element's UI. A `<list>` needs `enable-async-list` under this strategy, which the runtime sets on every list. The main-thread modules run on the engine thread too (below).

Release builds log only Lynx's warnings and errors. Lynx's iOS frameworks and Android AARs are built for release, where Lynx logs at INFO: a line for every touch move, hit test, flush, layout, event listener and main-thread module call, written as it's logged (`NSLog` on iOS, a call from native code into `android.util.Log` on Android), mostly on the engine thread and, during a touch, on the UI thread. So `AppDelegate` calls `SetMinimumLoggingLevel(.warning)` before anything else, under `#if !DEBUG`, and `ShellApplication` calls `LLog.setMinimumLoggingLevel(LLog.WARN)` when the app isn't debuggable, after `LynxEnv`'s init, which loads the native library the call needs. The development build (`ng serve --platform`) keeps every line. The app's JavaScript errors still reach the system log, since Lynx logs them as errors, and its `console` output is unchanged: Lynx writes that whatever the level.

Both send the same global props, which the runtime's services read: `platform`, `theme` (again whenever the phone switches between light and dark), `appLocale` (the phone's language as a BCP 47 tag), `appTimeZone` (its time zone's IANA name, which the `intl` build option's `Intl.DateTimeFormat` uses), `isNotchScreen`, `edgeToEdge`, the safe-area insets `safeAreaTop`, `safeAreaBottom`, `safeAreaLeft` and `safeAreaRight` (again whenever they change), `osVersion` (which Lynx leaves out of the main thread's `SystemInfo`), the accessibility settings `reduceMotion`, `reduceTransparency` (iOS only) and `increaseContrast`, again whenever the user changes one, `textScale` (the user's text size, `1` at the default: Dynamic Type's body size over its default on iOS, the font scale on Android, capped by angular.json's `textScaling.max`, `1` with `"textScaling": false`), again whenever it changes, `appState` (`active`, `inactive` or `background`, which `LynxAppState` reads, again as the scene's activation changes on iOS and as the activity starts, resumes, pauses and stops, or another window takes the focus, on Android), and `initialURL`, the link that started the app, if one did, with one of angular.json's `deepLinkSchemes` or an https link to its `appLinkDomains` (the scene's `connectionOptions.urlContexts`, or for a Universal Link its web browsing `userActivities`, on iOS, the launch intent's data on Android, unless the app was reopened from Recents), which `LynxLinking.getInitialURL()` returns and the router starts at. Android 12 and later also send `dynamicColors`, the wallpaper's Material 3 color roles in light and dark (`DynamicColors.kt`), again when the user changes their wallpaper or colors. Lynx Explorer sends `theme` and `isNotchScreen` too, but no `appLocale`, `appTimeZone`, `osVersion`, accessibility settings, `textScale` or `appState`. Both shells also set the `LynxView`'s font scale to `textScale`, at launch and with `updateFontScale` when it changes (Android keeps the activity through a font size change: the manifest's `configChanges` lists `fontScale`). The build tells Lynx to scale only `sp` lengths by it and writes the page's root font size in `sp`, so every `rem` follows the phone's text size and a `px` size stays as written. See [`templates/android/README.md`](templates/android/README.md) for the Android shell's details.

Both register the native modules the runtime's services call, which Lynx Explorer doesn't have: `AngularLynxWebAuth` (`WebAuthModule.swift`, `WebAuthModule.kt`) opens `LynxWebAuthSession`'s sign-in page, in `ASWebAuthenticationSession` on iOS and a Custom Tab on Android, and returns the URL it redirects to. `AngularLynxLocalStorage` (`LocalStorageModule.swift`, `LocalStorageModule.kt`) keeps `LynxLocalStorage`'s values in a `UserDefaults` suite and a `SharedPreferences` file of their own. `AngularLynxSecureStorage` (`SecureStorageModule.swift`, `SecureStorageModule.kt`) keeps `LynxSecureStorage`'s in the Keychain on iOS and, on Android, in `SharedPreferences`, each value encrypted with AES-GCM by an Android Keystore key, a file Auto Backup leaves out (`res/xml/backup_rules.xml`, `data_extraction_rules.xml`). `AngularLynxLinking` (`LinkingModule.swift`, `LinkingModule.kt`) opens `LynxLinking`'s links: `openURL` with `UIApplication.open` and an `ACTION_VIEW` intent, `openInApp` in `SFSafariViewController` and a Custom Tab, and `canOpenURL` with `UIApplication.canOpenURL` and `resolveActivity`, which answer only for the schemes the generator writes from angular.json's `canOpenURLSchemes` (with `http`, `https`, `mailto`, `tel` and `sms`) into Info.plist's `LSApplicationQueriesSchemes` and the manifest's `<queries>`. It also has `takeURLs`, which hands `LynxLinking.onURL()` and the router the links that open the app while it's running: `SceneDelegate.scene(_:openURLContexts:)` and `scene(_:continue:)` (a Universal Link), and `MainActivity.onNewIntent` (after a waiting web sign-in has had its redirect) keep each one (`LinkCenter` in `LinkingModule.swift`, the module's companion on Android) and send the `angularLynxURL` global event, which the runtime answers by taking them, as `LynxShortcuts` does. `AngularLynxImagePicker` (`ImagePickerModule.swift`, `ImagePickerModule.kt`) lets the person pick a photo for `LynxImagePicker`, with `PHPickerViewController` on iOS and the Photo Picker on Android, neither of which needs a permission, and calls back with it as base64, re-encoded as an upright JPEG when the app asks for a smaller one or the photo is a format such as HEIC. `AngularLynxShare` (`ShareModule.swift`, `ShareModule.kt`) opens `LynxShare`'s share sheet, `UIActivityViewController` on iOS and an `ACTION_SEND` chooser on Android, with the files written to temporary files on iOS and shared through a `FileProvider` on Android. Save Image on iOS needs `NSPhotoLibraryAddUsageDescription`, which the generator always writes (angular.json's `permissions.savePhotos`, with a default). `AngularLynxPhotoLibrary` (`PhotoLibraryModule.swift`, `PhotoLibraryModule.kt`) saves `LynxPhotoLibrary`'s image or video straight to the library: `PHAssetCreationRequest` with add-only access on iOS, and a MediaStore insert into `Pictures/<app name>` or `Movies/<app name>` on Android 10 and later, which needs no permission (it answers `unavailable` before Android 10). Only an app whose angular.json sets `permissions.savePhotos` has it: the generator's `leaveOut` deletes it from the others, with its registration between `MainActivity`'s `// angular-lynx:photo-library` markers, and iOS registers it by name. `permissions.photos` is iOS only (`NSPhotoLibraryUsageDescription`): Android declares nothing for it, since nothing in the shells reads the library and Google Play rejects `READ_MEDIA_IMAGES` without a core need. `AngularLynxBarcodeScanner` (`BarcodeScannerModule.swift`, `BarcodeScannerModule.kt`) reads a QR code or a barcode for `LynxBarcodeScanner` with the platform's own scanner, VisionKit's `DataScannerViewController` on iOS (16 and later) and Google's code scanner from Play services on Android (`play-services-code-scanner`, which needs no camera permission), and calls back with `{ format, value }`. Only an app whose angular.json sets `permissions.camera` has it: App Store Connect flags an app whose code uses the camera without `NSCameraUsageDescription` (ITMS-90683), so the generator's `configure` deletes the module from every other app, on Android with the library between `app/build.gradle.kts`'s `// angular-lynx:barcode-scanner` markers, and the shells register it by name (`NSClassFromString("AngularLynxBarcodeScannerModule")`, `Class.forName`), which builds either way. `AngularLynxShell` (`ShellModule.swift`, `ShellModule.kt`) has `hideSplashScreen`, which the runtime's `LynxSplashScreen` calls once the app's first screen is drawn (at Angular's first frame, or when `provideSplashScreen()` says): the phone takes a launch screen down at the app's first frame, which is the empty LynxView, so the iOS shell keeps a copy of it over the LynxView (`SplashScreen.swift`, the `LaunchBackground` color and `LaunchImage` image the generator writes from angular.json's `splash`) and Android's `MainActivity` keeps AndroidX's splash screen up (`installSplashScreen()`, `setKeepOnScreenCondition`), each fading it out when it's called, or five seconds after the app starts. It has `collectGarbage`, which the runtime calls once the app has released about a screen's worth of elements and settled: it reports moderate memory pressure with `LynxEnv.trimMemory`, which makes Lynx run a full collection of the main thread's JavaScript heap, freeing what PrimJS's routine collections leave behind of the screens that went. It has `markEvent(name)`, which marks a moment the app names in a system trace: an `os_signpost` event named `Mark` with the name as its message, in the Points of Interest category Instruments shows (os_signpost's names are fixed when the shell is compiled), and on Android an instant `Trace` section of that name, which Perfetto shows, and a `Mark <name> at <ns> ns` line in logcat, with `SystemClock.elapsedRealtimeNanos()` at the call (logcat shows no trace sections), as its `reportFullyDrawn` logs `Fully Drawn at <ns> ns` beside the system's own `Fully drawn` line, which gives no clock time. The runtime doesn't call it; the benchmark apps mark their mount screen's start with it (`benchmarks/SPEC.md`), for the harness to time the screen apart from the launch. On Android it also connects the back button. Both shells report the system's memory warnings to `trimMemory` too, and leaving the screen. `AngularLynxShortcuts` (`ShortcutsModule.swift`, `ShortcutsModule.kt`) keeps the shortcuts the person ran until the runtime's `LynxShortcuts` takes them, with `take`, at startup and each time the shell sends the `angularLynxShortcut` global event, so the shortcut that started the app isn't lost and none is handled twice. The generator writes angular.json's `shortcuts` as App Intents on iOS (`App/AppShortcuts.swift`, with an `AppShortcutsProvider`: Xcode's App Intents step reads the titles and phrases out of the compiled code, so they have to be source), which Siri, Spotlight and the Shortcuts app run, and as static shortcuts on Android (`res/xml/shortcuts.xml`, with the titles in `res/values/shortcuts.xml`), in the menu a long press on the app's icon opens. Android starts a static shortcut's activity in a cleared task, which would end the running app, so they point at `ShortcutActivity`, which has a task of its own and passes the shortcut on to `MainActivity`.

`AngularLynxBiometrics` (`BiometricsModule.swift`, `BiometricsModule.kt`) is `LynxBiometrics`' prompt and the store for `LynxSecureStorage`'s `requireBiometrics` values (issue #918). `availability` reports the sensor (`LAContext.biometryType`; on Android `BiometricManager.canAuthenticate(BIOMETRIC_STRONG)` and the package manager's fingerprint, face and iris features), whether a face or finger is enrolled, and whether the phone has a passcode. `authenticate` shows `LAContext.evaluatePolicy` (biometrics only, with the "Enter Password" fallback hidden, or `.deviceOwnerAuthentication` with `allowDeviceCredential`) or AndroidX's `BiometricPrompt`, strong biometrics only, which is why `MainActivity` is a `FragmentActivity`. The store keeps each value on iOS as a Keychain item of its own service with `SecAccessControl(.biometryCurrentSet)` and `kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly`, read with an `LAContext` whose `localizedReason` is the app's (a missing key is found from its attributes first, which don't ask), and on Android sealed with AES-GCM under a key of its own, which RSA-OAEP wraps under a Keystore key pair that needs a strong biometric for each use (`setUserAuthenticationRequired`, `setInvalidatedByBiometricEnrollment`): storing uses the public key and doesn't prompt, and reading unwraps through `BiometricPrompt`'s `CryptoObject`. Enrolling a new face or finger invalidates the item or the pair, and the values then read as none. Only an app with angular.json's `permissions.biometrics` has the module: the generator (`leaveOut`) deletes `BiometricsModule.swift` (`IOS_BIOMETRICS_SOURCES`), or `BiometricsModule.kt` (`ANDROID_BIOMETRICS_SOURCES`), `res/values/biometrics.xml` (the prompt's default reason, which it writes from the permission) and the lines between the `// angular-lynx:biometrics` markers of `MainActivity.kt` and `app/build.gradle.kts` (its registration and AndroidX Biometric) from the others, and LynxViewController registers it by its Objective-C name (`AngularLynxBiometricsModule`). That keeps `LocalAuthentication` out of an iOS app with no `NSFaceIDUsageDescription`, without which Face ID fails.

Only the development build (`ng serve --platform`) loads from a dev server: the code is in `App/DevServer.swift` and `App/DevServerModules.swift` under `#if DEBUG`, and in the debug source set on Android (`app/src/debug`, with a no-op `DevServer` in `app/src/release`), so a release build can't be pointed anywhere else. `DevServer` reads the URL from the launch argument or intent extra and keeps it (`UserDefaults`, `SharedPreferences`), so the app opened from the home screen loads from the same server. The loaders (`BundleResourceFetcher.swift`, `ResourceFetchers.kt`) and `AngularLynxAssets` then fetch every relative URL, and on Android every URL on the address the bundle was built with, from the dev server instead of the app, uncached. When the bundle itself doesn't load, `DevServer` covers the page with a message and loads it again every two seconds. rspeedy's live reload client talks to Lynx DevTool, which the shells don't have: `NativeModules.LynxWebSocketModule` (through `@lynx-js/websocket`) for the dev server's socket and `NativeModules.LynxDevToolSetModule.invokeCdp` for a full reload (a DevTool protocol `Page.reload`). The development build registers modules under those names (`DevWebSocketModule`, `DevReloadModule`): a WebSocket with `URLSessionWebSocketTask` and OkHttp that sends the same `websocketOpen`, `websocketMessage`, `websocketClosed` and `websocketFailed` global events as Lynx DevTool's, and a `Page.reload` that loads the bundle again, as DevTool's `LynxPageReloadHelper` does. URLSession sends an empty `Sec-WebSocket-Protocol` header for an empty protocol list, which the dev server refuses, so the iOS socket passes none then. On Android, the debug build's `network_security_config.xml` allows plain HTTP to any host, since the app's own `fetch()` of an imported file goes to the address the bundle was built with; the release build's allows it to `localhost` alone.

`AngularLynxClipboard` (`ClipboardModule.swift`, `ClipboardModule.kt`) copies `LynxClipboard`'s text to `UIPasteboard.general` on iOS and `ClipboardManager` on Android, and reads it back.

`AngularLynxFilePicker` (`FilePickerModule.swift`, `FilePickerModule.kt`) is `LynxFilePicker`'s document picker and save screen (issue #924): `UIDocumentPickerViewController(forOpeningContentTypes:asCopy:)` and `(forExporting:asCopy:)` on iOS, with the runtime's types (MIME types, `image/*` families, `.ext` extensions) as `UTType`s, and `ACTION_OPEN_DOCUMENT` and `ACTION_CREATE_DOCUMENT` on Android, through one `StartActivityForResult` launcher in `MainActivity`, with extensions looked up in `MimeTypeMap`. Neither needs a permission. A pick sums the documents' sizes before reading any and answers `too-large` over the runtime's `maxBytes`; the bytes go each way as base64. An app opts in with angular.json's `filePicker`: without it, the generator deletes both files and the lines between `MainActivity.kt`'s `// angular-lynx:file-picker` markers, and `LynxViewController` finds no `AngularLynxFilePickerModule` class to register. `fileSharing` adds `UIFileSharingEnabled` and `LSSupportsOpeningDocumentsInPlace` to Info.plist, which lists the app's Documents folder in Files.

`AngularLynxHaptics` (`HapticsModule.swift`, `HapticsModule.kt`) plays `LynxHaptics`' feedback: `UIImpactFeedbackGenerator`, `UISelectionFeedbackGenerator` and `UINotificationFeedbackGenerator` on iOS, each kept and prepared again after it plays, and `View.performHapticFeedback()` on the activity's window on Android, which needs no permission and follows the person's touch feedback setting.

`AngularLynxStoreReview` (`StoreReviewModule.swift`, `StoreReviewModule.kt`) asks for `LynxStoreReview`'s rating prompt: `AppStore.requestReview(in:)` on iOS 16 and later and `SKStoreReviewController.requestReview(in:)` before, over the window scene in the foreground, and Google Play's In-App Review API (`com.google.android.play:review`) on Android, launched over the activity. Each calls back `{}` once the request is made, since neither store says whether it showed anything. An app opts in to it: without angular.json's `storeReview`, the generator deletes both files, the lines between `MainActivity.kt`'s and `app/build.gradle.kts`'s `// angular-lynx:store-review` markers, which register the module and add Play's library, and `LynxViewController` finds no `AngularLynxStoreReviewModule` class to register.

`AngularLynxCalendar` (`CalendarModule.swift`, `CalendarModule.kt`) opens the system's event editor for `LynxCalendar.addEvent()`, filled in with the app's event (title, start and end in milliseconds since 1970, all-day, location, notes): EventKitUI's `EKEventEditViewController` on iOS 17 and later, which runs outside the app and saves the event itself, so the app needs no calendar permission or usage description, and an `ACTION_INSERT` on `CalendarContract.Events` on Android, which the calendar app's own editor takes. iOS calls back `{ result: "saved" }` or `"canceled"`, from the editor's delegate or a swipe down; before iOS 17 the editor needs full calendar access, so it answers `{ error: "unavailable" }`. Android calls back `"saved"` only when the calendar app answers `RESULT_OK`, and `"unknown"` otherwise, since Google Calendar answers `RESULT_CANCELED` either way, or `{ error: "unavailable" }` without a calendar app. `MainActivity` registers the `StartActivityForResult` launcher as it's created, as the image picker's, and passes the module a `CalendarModule.Host`. An app opts in to it with angular.json's `calendar`: without it, the generator deletes both files and the lines between `MainActivity.kt`'s `// angular-lynx:calendar` markers, and `LynxViewController` finds no `AngularLynxCalendarModule` class to register.

`AngularLynxAppleSignIn` (`AppleSignInModule.swift`, iOS only) opens `LynxAppleSignIn`'s Sign in with Apple sheet: an `ASAuthorizationAppleIDProvider` request with the scopes, nonce and state asked for, presented by an `ASAuthorizationController` over the key window. It calls back the user identifier, the identity token and authorization code as UTF-8 text, the email and the shared parts of the name when Apple gives them, and `realUserStatus`, or `{ error: 'canceled' | 'failed', message }`. `credentialState` answers `getCredentialState(forUserID:)`, and `available` answers `{ available: true }`. The sheet needs the `com.apple.developer.applesignin` entitlement, which a free Personal Team can't sign, so without angular.json's `signInWithApple` the generator deletes the file and writes no entitlement, and `LynxViewController` finds no `AngularLynxAppleSignInModule` class to register. Android has no module: the runtime rejects with `unsupported` there.

`Config/App.entitlements` is written from `IOS_ENTITLEMENTS` in `src/ios/project.ts`: each option that needs a capability (`appLinkDomains`' Associated Domains, `signInWithApple`) names its Xcode capability and the entitlements it adds, and `mergeEntitlements` joins them into one file, two options' lists under one key becoming one list. The file, and `CODE_SIGN_ENTITLEMENTS` in the xcconfig, are written only when some option adds an entitlement, so an app that needs none signs with none. A signing error about a capability a Personal Team can't sign names the option that added it (`explainSigningFailure` in `src/ios/build.ts`).

Both link Lynx's XElement library, which holds `<input>`, `<textarea>`, `<overlay>`, `<svg>`, `<blur-view>`, `<viewpager>`, `<refresh>`, the `<scroll-coordinator>` family, `<webview>` and `<video>`. Lynx's core doesn't include these, and a host that doesn't register them renders nothing for those tags (on Android, nothing after them either). XElement's AnimaX and Markdown elements are left out: the runtime doesn't support them. On iOS, `<blur-view>` is XElement's with more of UIKit in it (`App/BlurView.swift`): a `blur-material` attribute for UIKit's adaptive blur materials, which the glass components draw their design before iOS 26 on (Lynx's blur-view has only the styles from before iOS 13); Liquid Glass that materializes, dissolves and eases between effects inside a `glass-container`, where Lynx's sets its effect at once; and a `glass-effect-id` attribute that pairs two glass shapes across a change so one morphs into the other (`App/GlassTransitions.swift`). `<video>` is XElement's with its frames readable by a canvas, so `drawImage()` and WebGL's `texImage2D()` (three.js's `VideoTexture`) read the frame it shows (`App/AngularLynxVideo.m`, `VideoUI.kt`; issue #696). `<webview>` loads through XElement's loader, wrapped (`App/WebViewLoader.swift`) to take the loader off its web view's script message handlers when the element goes: XElement's loader never does, so the loader and the web view kept each other, and the web view's WebContent process, for as long as the app ran (issue #397).

Both have `<canvas>` with WebGL2 (issue #211), which Lynx doesn't: a `canvas` element (`App/AngularLynxWebGL.m`'s `AngularLynxCanvas`, a `CAMetalLayer` view; `CanvasUI.kt`, a `TextureView`) and the `AngularLynxWebGL` module the runtime's WebGL2 context sends its calls to, which runs them on OpenGL ES 3.0 (`App/AngularLynxWebGLContext.m`, `WebGLContext.kt`). On iOS that's [ANGLE](https://chromium.googlesource.com/angle/angle)'s OpenGL ES, on Metal, which Safari draws WebGL with too: iOS's own OpenGL ES is deprecated, and the Simulator runs it on the CPU, at seconds a frame for a lit three.js scene (issue #238), where Metal draws on the Mac's GPU. ANGLE's `libEGL` and `libGLESv2` frameworks, and its headers, come in the Lynx frameworks zip (below). Android's OpenGL ES is the phone's, which the emulator already runs on the Mac's GPU. The runtime runs on Lynx's main thread and WebGL needs answers synchronously, so both turn on main-thread modules (`enableMTSModule`): the config's modules are then callable from main-thread JavaScript as `lynx.module(name)`, and Lynx calls them on its engine thread, not the UI thread. An EGL context is current on one thread at a time, so GL runs there too, while the canvas's view lives on the UI thread. On iOS the view hands the context what it draws into, its `CAMetalLayer` and its size in pixels (`AngularLynxCanvasTarget`), through Lynx's `runOnTasmThread:`, so the contexts and the canvas registry are the engine thread's alone, and the context keeps its EGL context current there between batches; it sets the view's opacity back on the UI thread. On Android each call already makes the context current and puts back what was current before, so `WebGLContext` and `CanvasRegistry` are locked instead: the `TextureView`'s surface callbacks, on the UI thread, wait for a batch to end, which keeps the EGL surface from outliving the `SurfaceTexture` it draws to. The WebGL module's `encodeImage`, behind `canvas.toBlob()` and `toDataURL()`, reads the drawing buffer and encodes it as a PNG or JPEG with ImageIO or `Bitmap.compress`. On iOS it, and `readPixels()` into an array, read through a pixel pack buffer of their own, mapped, since ANGLE on Metal is slow to read straight into memory; a `readPixels()` that GL rejects answers nothing, so the app's array keeps what it held, as WebGL leaves it. The same module has the runtime's 2D context (issue #469): `create2D`, `run2D`, `destroy2D` and `encode2D` draw into a bitmap with Core Graphics (`App/AngularLynxCanvas2DContext.m`) or `android.graphics.Canvas` (`Canvas2DContext.kt`), and show it in the canvas's view after each task that drew: a copy in a `CALayer` over the `CAMetalLayer` on iOS, drawn into the `TextureView`'s surface with `lockHardwareCanvas()` on Android. Both kinds of context implement `AngularLynxCanvasContext` / `CanvasContext`, which the canvas registry pairs with views and which another context reads a canvas through (`snapshot`), for `drawImage()` and for `texImage2D()` with a canvas. The module's `imageFromCanvas` copies a canvas's snapshot under an image id, as `decodeImage` keeps a file's pixels, for `createImageBitmap()` of a canvas and `OffscreenCanvas.transferToImageBitmap()`, which then clears the canvas (`clearForTransfer`); `imageFromImage` copies an image it already keeps (an ImageBitmap's, an `Image`'s), and `imageFromPixels` keeps an ImageData's bytes, for `createImageBitmap()` of those. Each of the four takes createImageBitmap's crop rectangle (`pixelsOfSnapshot` crops before it resizes and flips) and answers `cropped` when it applied one. A third kind of context, `bitmaprenderer` (`App/AngularLynxBitmapRendererContext.m`, `BitmapRendererContext.kt`), takes a decoded image off the module with `transferToBitmapRenderer`, for `transferFromImageBitmap()`, and shows it as the 2D context shows its bitmap (on Android, both through `BitmapPresenter.kt`); its snapshot is that image, so other contexts read the canvas as it. Its command numbers (`App/AngularLynxCanvas2DOps.h`, `Canvas2DOps.kt`) are generated from `canvas/canvas-2d-ops.ts` by the same script. The canvas code is the part of the shells an app leaves out by what its bundle uses (issue #837), as the biometrics module is left out by what angular.json asks for (above): about 176 kB of the iOS executable, and ANGLE. The build plugin writes `.angular-lynx-native.json` beside the bundle, with `"canvas": false` when none of the bundle's main-thread modules names a canvas (`native-features.ts` in the plugin: the names that bring in the runtime's WebGL2 and 2D contexts, `'canvas'`, `Image`, `createImageBitmap` and the like). Then the generator (`leaveOut` in `src/ios/project.ts` and `src/android/project.ts`) deletes the canvas sources, `App/AngularLynx*.{h,m}` (`IOS_CANVAS_SOURCES`) and the Kotlin files of `ANDROID_CANVAS_SOURCES`, with `<video>`'s frame readers, which only a canvas reads. On iOS it also takes the ANGLE frameworks out of the project. On Android it takes out the lines that register them, between `MainActivity.kt`'s `// angular-lynx:canvas` markers. The iOS shell's Swift reaches the Objective-C classes only by name (`NSClassFromString`), so it registers no canvas, and keeps XElement's own `<video>`, when they're gone. With no file (an older plugin, another build) or a development app (`ng serve --platform`, which gets every edit), the app has everything, and so does an ejected project: the eject schematic renders it with `renderEjectedProject()` and no `features`, since it's the user's to grow, and the builder builds it as it is. A script that renders a project only to build it passes `features` to leave the same code out (the benchmark's ReactLynx iOS app, issue #858). The file is in the generated project's input hash, so an app that starts drawing regenerates with the code back in. An app that draws only in 2D keeps the canvas and leaves out the WebGL2 context (issue #847): the file says `"webgl": false` when no main-thread module names `webgl2`, `WebGL2RenderingContext` or `ɵenableWebGL2`. Then the generator deletes `App/AngularLynxWebGLContext.m` and `App/AngularLynxWebGLOps.h` (`IOS_WEBGL_SOURCES`) and takes ANGLE out of the iOS project, or deletes `WebGLContext.kt` and `WebGLOps.kt` (`ANDROID_WEBGL_SOURCES`), and takes out the lines that name the context, between the `// angular-lynx:webgl` markers of `App/AngularLynxWebGL.h` and `.m` and of `WebGLModule.kt`. The 2D context needs neither: it draws with Core Graphics, shown in a `CALayer` over the canvas's `CAMetalLayer`, which is QuartzCore's, and with `android.graphics.Canvas`. A file from an older plugin, with `"canvas": true` and no `webgl`, keeps WebGL. `AngularLynxAssets` (`App/AssetsModule.swift`, `AssetsModule.kt`) reads a file the app bundles for the main thread's `fetch`, which has no page URL to resolve `/static/...` against. The command numbers the WebGL module reads (`App/AngularLynxWebGLOps.h`, `WebGLOps.kt`) are generated from the runtime's `canvas/webgl-ops.ts` with `npm run generate:webgl-ops -w packages/native`; `scripts/webgl-ops.test.ts` fails when they're stale. UIKit's module imports Apple's OpenGL ES headers into every file, so `AngularLynxWebGLContext.m` turns off their deprecation warnings, which land on ANGLE's functions of the same names; the explicit link to `libGLESv2` comes before UIKit's automatic one to OpenGLES, so those calls bind to ANGLE.

## Lynx for iOS

Lynx publishes iOS only as source pods, which take minutes to compile and need CocoaPods (and so Ruby). `scripts/build-lynx-ios-frameworks.sh` compiles them once into XCFrameworks (about 32 MB zipped, with debug symbols in a separate zip): Lynx, PrimJS, XElement and their dependencies, and ANGLE's `libEGL` and `libGLESv2`, with ANGLE's headers in `ANGLE/include`. The builder downloads the zip pinned in `src/ios/frameworks.ts` (URL and SHA-256) on first use and caches it in `~/.cache/angular-lynx/lynx-ios/<version>-<build>`.

ANGLE only builds with Chromium's tooling (depot_tools, GN and Ninja), so the Lynx script runs `scripts/build-angle-ios-frameworks.sh`, which checks out the ANGLE revision a Chrome stable release shipped (`ANGLE_REVISION`), builds its Metal backend alone for the device and both Simulator architectures, with ANGLE's own Metal shaders prebuilt (otherwise it compiles them when an app first makes a context, which took 5.7 s on a fresh install in the Simulator), and leaves out the dependencies ANGLE's DEPS fetches for its tests and other backends. The checkout is about 5 GB and the three builds take about a minute and a half together; run it alone (`npm run build:angle-ios-frameworks -w packages/native`) to try a new revision. ANGLE adds about 6 MB to an app (2 MB compressed in the `.ipa`), against Lynx's 34 MB, so only an app that draws with WebGL links it (below).

The zip for Lynx 4.1.0 is the [`lynx-ios-4.1.0-3` release](https://github.com/Blotch-Smart-Frames/AngularLynx/releases/tag/lynx-ios-4.1.0-3). The build number counts rebuilds of one Lynx version whose frameworks changed (2 added XElement, 3 ANGLE), and is part of the cache folder, so machines with an older zip download the new one. For a new Lynx version, bump the versions in the script and reset `BUILD` to 1; to change the frameworks of the same version, bump `BUILD` (in the script and in `LYNX_IOS`). Then run the **Lynx iOS frameworks** workflow with `publish` (or the script locally), and pin the new zip's URL and SHA-256. To test a locally built folder before publishing it:

```sh
npm run build:lynx-ios-frameworks -w packages/native   # needs Xcode, Ruby >= 2.7 with Bundler for CocoaPods, and Python 3 for ANGLE (the script downloads Xcode's Metal toolchain if it's missing)
export ANGULAR_LYNX_IOS_FRAMEWORKS=$PWD/packages/native/.lynx-ios-build/out/LynxFrameworks
```

## Changing a template

- **iOS:** `App/` is a synchronized folder, so adding or removing a Swift file needs no project change. For anything else (a build setting, a framework, a resource folder), edit `APP_PROJECT` in `scripts/generate-ios-project.ts`. `App.xcodeproj` isn't in git: the `iosTemplateProject` Vite plugin in `vite.config.ts` renders it with [`@bacons/xcode`](https://github.com/EvanBacon/xcode), which needs only Node, on every `npm run build` and `npm test`, and the npm package ships the result. Run `npm run generate:ios-project -w packages/native` to render it without the TypeScript build, e.g. to open the template in Xcode.
- **Both:** run `npm run e2e -- --ios --shell` (and Layer 6 for Android, see the [E2E README](../e2e/README.md)) to build and tap through a fresh app on each platform.
