# Android shell template

The Android app that `ng build --platform android` builds. The generator copies this folder into `.angular/cache/<Angular version>/<project>/lynx-native/android`, fills in the few files below, and runs Gradle. Everything else is static: it's code we own and test, not something users edit (they can `eject` to get a copy they own).

The app is one activity holding one full-screen `LynxView` that runs `main.lynx.bundle`. Angular Router does all navigation inside it.

## What the generator changes

| What            | Where                                                         | Notes                                                                                                                                                                                                                                                                                                                                               |
| --------------- | ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The bundle      | `app/src/main/assets/`                                        | The whole `dist/` folder (`main.lynx.bundle`, `static/…`), copied after emptying the folder. Bundled files are read from here.                                                                                                                                                                                                                      |
| App identity    | `angular-lynx.properties`                                     | Keys: `applicationId`, `versionName`, `versionCode`, `appName`, `screenOrientation` (`portrait`, `sensorLandscape` or `unspecified`). Read by `app/build.gradle.kts`. The committed file holds defaults.                                                                                                                                            |
| Permissions     | `AndroidManifest.xml`, at `<!-- angular-lynx:permissions -->` | `<uses-permission>` lines. `INTERNET` is always declared.                                                                                                                                                                                                                                                                                           |
| Deep links      | `AndroidManifest.xml`, at `<!-- angular-lynx:deep-links -->`  | `<intent-filter>`s inside the main activity.                                                                                                                                                                                                                                                                                                        |
| Shortcuts       | `res/xml/shortcuts.xml`, `res/values/shortcuts.xml`           | One `<shortcut>` per entry of angular.json's `shortcuts`, and a string for its title. The committed `shortcuts.xml` is an empty list.                                                                                                                                                                                                               |
| Splash screen   | `res/values*/colors.xml`, `res/drawable-*/splash_icon.png`    | angular.json's `splash`: its colors as `window_background` (`values/`, `values-night/`), and its image drawn on a transparent 288 dp canvas at each density, in place of `res/values/splash.xml`'s alias to the launcher icon.                                                                                                                      |
| SDK location    | `local.properties`                                            | `sdk.dir=…`, unless `ANDROID_HOME` is set.                                                                                                                                                                                                                                                                                                          |
| Release signing | Gradle properties, from the environment                       | `ORG_GRADLE_PROJECT_angularLynxStoreFile`, `…StorePassword`, `…KeyAlias`, `…KeyPassword` (no dots: dash, `/bin/sh` on Debian and Ubuntu, drops variables whose names aren't shell identifiers before `gradlew` starts Gradle). Never written to disk. Without all four, release builds are signed with the debug key (installable, not uploadable). |

Build commands and outputs (no flavors, so the names are fixed):

```sh
./gradlew :app:assembleDebug                      # app/build/outputs/apk/debug/app-debug.apk
./gradlew :app:assembleRelease :app:bundleRelease # app/build/outputs/apk/release/app-release.apk
                                                  # app/build/outputs/bundle/release/app-release.aab
```

The release build runs R8 and the resource shrinker (`isMinifyEnabled`, `isShrinkResources`), and writes the mapping that turns the renamed classes back to `app/build/outputs/mapping/release/mapping.txt`, which also goes in the `.aab` for Google Play. Lynx's AAR ships keep rules for its own classes; `app/proguard-rules.pro` adds the ones they miss, each with what broke without it (the app aborting on launch, for one). Any class Lynx or the shell reaches only by name needs a rule there. How they were found, and the sizes, are in `investigations/native-app-builds.md` ("R8 in the Android release build").

A release build signed with the upload key holds only `arm64-v8a` and `armeabi-v7a` (`ndk.abiFilters`). Google Play rejects an app whose 64-bit native libraries aren't aligned for 16 KB memory pages, and Fresco's `x86_64` libraries, at the version Lynx's image service is written against, are aligned for 4 KB only; its `arm64-v8a` ones, and all of Lynx's, are fine. So Play doesn't offer the app to x86 devices (emulators and a few Chromebooks). A release build signed with the debug key keeps all four ABIs, so its APK still installs on an `x86_64` emulator. Drop the filter once the image service moves to a Fresco whose `x86_64` libraries are 16 KB aligned.

## How the shell loads the app

- **Bundles** come from `assets/` (`ResourceFetchers.kt`, `BundleAssets.kt`). A URL without a scheme (`/static/…`, `static/…`), `asset:///…` and `file:///android_asset/…` all mean "the file at that path in `assets/`", so the bundle works with Rspeedy's default asset prefix (`/`) and doesn't need a platform-specific one. Absolute `http(s)` URLs are fetched with OkHttp.
- **`fetch()` and `XMLHttpRequest`** go through Lynx's HTTP service (`LynxHttpService`, registered in `ShellApplication.kt`), which uses OkHttp. Plain HTTP is allowed to `localhost` and `127.0.0.1` only (`res/xml/network_security_config.xml`), for a server on the device or one on your machine through `adb reverse`; every other host needs HTTPS, Android's default.
- **Images** are loaded by Fresco. The media fetcher rewrites bundled image URLs to `asset:///…`, which Fresco reads from the APK.
- **Lazy routes** need nothing extra: the build plugin keeps each lazy chunk inside `main.lynx.bundle` (see `split-chunks.ts` in the build plugin). Bundles requested by URL at runtime still go through the template resource fetcher.

## Back button

Back is off by default, so it leaves the app like any root screen. The runtime turns it on while the Router has history or something open on top takes back (a handler registered with `LynxBackButton.on()`, such as a popover's) by calling `NativeModules.AngularLynxShell.setBackHandlerEnabled(true)`, and off again otherwise (`LynxBackButton` in `packages/runtime/src/lib/back-button/back-button.ts`, which `provideRouter()` starts; the call goes through the background thread, where `NativeModules` lives). While it's on, a back press sends the global event `angularLynxBack` instead, which the runtime gives to the handler registered last, or turns into `Location.back()`. The app has to say beforehand because Android decides synchronously, at the start of the gesture, whether an app handles back (predictive back animates differently). While it's on, Android's predictive back gesture (Android 14 and later) also reaches the app as it goes: `handleOnBackStarted`, `handleOnBackProgressed` and `handleOnBackCancelled` send the global event `angularLynxBackGesture` with `{ phase: 'started' | 'progressed', progress, edge }`, or `{ phase: 'canceled' }` alone (`handleOnBackCancelled` has no `BackEventCompat`), and a `<lynx-stack-outlet>` moves its top page with it. The manifest's `android:enableOnBackInvokedCallback="true"` opts Android 14 and 15 in to that; Android 16 does it for an app that targets API 36. A gesture that ends in back sends `angularLynxBack`, as a press does. Layer 6's `native/back-button.yaml` checks both ends.

## Splash screen

`MainActivity` starts with the theme `Theme.AngularLynxShell.Starting` (`res/values/themes.xml`), a child of AndroidX `core-splashscreen`'s `Theme.SplashScreen`, which draws Android 12's splash screen on every version from 7: `window_background` with `splash_icon` in the middle, the launcher icon unless angular.json's `splash` has an image. `installSplashScreen()`, before `super.onCreate`, switches it to the app's theme. Android would take the splash down at the first frame, the empty LynxView, so `setKeepOnScreenCondition` holds it until the runtime calls `NativeModules.AngularLynxShell.hideSplashScreen()` (`LynxSplashScreen` in `packages/runtime`, once the app's first screen is drawn), a development build's message shows, or five seconds pass. The exit animation fades it out over 250 ms, as the iOS shell does.

Android shows a splash icon without an icon background in a 288 dp square, cut to the circle 192 dp across in its middle. The generator draws the image at `splash.imageWidth` dp on a 288 dp canvas, smaller if its corners would reach past the circle (the build warns then), so a logo is never cropped.

## Memory

PrimJS, which runs the app's JavaScript on Lynx's main thread, collects garbage as the app runs, but those collections leave behind much of what a screen leaves when it goes, so native memory grows with every screen the app shows. Lynx runs a full collection, which frees it, when the host reports memory pressure with `LynxEnv.trimMemory`. The runtime asks for one through `NativeModules.AngularLynxShell.collectGarbage()` (`ShellModule.kt`, which reports moderate pressure) once the app has released about a screen's worth of elements and settled (`collect-garbage.ts` in `packages/runtime`), and `ShellApplication.kt` reports the system's `onTrimMemory` and `onLowMemory`, including the app leaving the screen.

## Web sign-in

`NativeModules.AngularLynxWebAuth.start(request, callback)` (`WebAuthModule.kt`, behind the runtime's `LynxWebAuthSession`) opens `request.url` in a Custom Tab (`androidx.browser`). The page's redirect to `request.callbackScheme` comes back as a deep link: the activity is `singleTask`, so the intent reaches the open one in `onNewIntent`, which hands the URL to the callback, and starting it closes the Custom Tab above it. That's why the scheme has to be in the app's `deepLinkSchemes`. Android says nothing when a Custom Tab is closed, so the activity resuming with a session still open, after having gone behind the tab, means the person canceled. iOS's `WebAuthModule.swift` reports the same results through `ASWebAuthenticationSession`.

## Links

`NativeModules.AngularLynxLinking` (`LinkingModule.kt`, behind the runtime's `LynxLinking`) opens links outside the app. `MainActivity` registers it with itself as the param, since the module starts activities from it and watches its lifecycle. Its `takeURLs(callback)` calls back with `{ urls }`, the links with one of angular.json's `deepLinkSchemes`, and the App Links to its `appLinkDomains`, that arrived while the app was open: `MainActivity.onNewIntent` keeps each one with the module and sends the `angularLynxURL` global event, which the runtime answers by taking them. The link that started the app goes in the `initialURL` global prop instead, read from the intent in `onCreate` unless the app was reopened from Recents.

- **`openURL(url, callback)`** starts an `ACTION_VIEW` intent, which the browser, the mail app or the app that claims the URL opens, and calls back with `{}`, or with `{ error, message }` when nothing does.
- **`openInApp(url, options, callback)`** opens an http(s) URL in a Custom Tab, with `options.toolbarColor` as its toolbar color. Android says nothing when a Custom Tab closes, so the module watches the activity's lifecycle and calls back when it resumes after pausing for the tab: the person closed the tab or came back to the app another way. It doesn't touch `WebAuthModule`'s session, which `MainActivity` tracks on its own.
- **`canOpenURL(url, callback)`** asks `resolveActivity`, which from Android 11 sees only the apps the manifest's `<queries>` names: one `VIEW` intent per scheme, which the generator writes between the `angular-lynx:queries` markers from angular.json's `canOpenURLSchemes`, after `http`, `https`, `mailto`, `tel` and `sms`. Starting an activity needs no `<queries>`.

iOS's `LinkingModule.swift` does the same with `UIApplication.open`, `SFSafariViewController` and `UIApplication.canOpenURL`, which answers only for the schemes in Info.plist's `LSApplicationQueriesSchemes`.

## Shortcuts

angular.json's `shortcuts` are the app's static shortcuts, in the menu a long press on its icon opens: the manifest's `android.app.shortcuts` meta-data on `MainActivity` points at `res/xml/shortcuts.xml`, which the generator writes. Static ones are there from the moment the app is installed. Each takes the app's icon, since the launcher draws an empty circle for a shortcut without one.

- **A shortcut points at `ShortcutActivity`, not `MainActivity`.** Android starts a static shortcut's activity with `FLAG_ACTIVITY_NEW_TASK` and `FLAG_ACTIVITY_CLEAR_TASK`, which an app can't change, so pointing at `MainActivity` would end the open one, and the running Angular app with it. `ShortcutActivity` has a task of its own to clear (`taskAffinity=""`, out of Recents, `Theme.NoDisplay`), starts `MainActivity` the ordinary way with the shortcut's extras, and finishes. The open `MainActivity` gets them in `onNewIntent`. It isn't exported: the launcher starts a shortcut as the app itself.
- **`NativeModules.AngularLynxShortcuts.take(callback)`** (`ShortcutsModule.kt`, behind the runtime's `LynxShortcuts`) calls back with `{ shortcuts }`: each one that ran since the last call, as `{ id, route? }`. `MainActivity` leaves a shortcut with the module and, when the app is open, sends the `angularLynxShortcut` global event, which the runtime answers by taking them. It also takes them once as it starts, which is how the shortcut that started the app arrives.
- **A recreated activity doesn't run its shortcut again.** Android hands an activity the intent it started with when it recreates it, and when the app is reopened from Recents, so `onCreate` only takes the shortcut from a first start that didn't come from history.

iOS's shell does the same with App Intents: the generator writes `App/AppShortcuts.swift`, whose intents open the app and leave their shortcut with `ShortcutsModule.swift`'s `ShortcutCenter`.

## Storage

`NativeModules.AngularLynxLocalStorage` and `NativeModules.AngularLynxSecureStorage` (`LocalStorageModule.kt` and `SecureStorageModule.kt`, behind the runtime's `LynxLocalStorage` and `LynxSecureStorage`) keep string values, which the runtime stores as JSON, each in a `SharedPreferences` file of its own. Each method calls back once with `{ value }`, `{}` or `{ error }`.

- **Secure values are encrypted with AES-GCM** by a key the Android Keystore makes the first time and never lets out, with the value's key as the associated data. Android's `EncryptedSharedPreferences` did the same, but `androidx.security:security-crypto` is deprecated. The secure module works on one background thread shared by every LynxView, since the Keystore can be slow, so calls run in order.
- **Auto Backup leaves out the secure file** (`res/xml/backup_rules.xml` up to Android 11, `data_extraction_rules.xml` from 12): the key can't leave the device, so a restored copy couldn't be decrypted. A value that won't decrypt anyway is removed and read as none.

iOS's `LocalStorageModule.swift` uses a `UserDefaults` suite and `SecureStorageModule.swift` the Keychain, readable after the first unlock and never moved to another device.

`NativeModules.AngularLynxBiometrics` (`BiometricsModule.kt`, behind the runtime's `LynxBiometrics` and `LynxSecureStorage`'s `requireBiometrics`) shows AndroidX's `BiometricPrompt` over `MainActivity`, which is a `FragmentActivity` for it, with strong (Class 3) biometrics only, and the device credential beside them with `allowDeviceCredential` (beside weak ones on Android 9 and 10, which take no other pair). Its values are in a `SharedPreferences` file of their own, `angular_lynx_biometric_storage`, which Auto Backup leaves out too: each is sealed with AES-GCM under a fresh key, which RSA-OAEP wraps under a Keystore key pair whose private key needs a strong biometric for each use. Storing uses the public key, outside the Keystore, so it doesn't prompt; reading unwraps the key through the prompt's `CryptoObject`. A new fingerprint or face invalidates the pair (`KeyPermanentlyInvalidatedException`), and the module then forgets every value. Only an app with angular.json's `permissions.biometrics` has the module, its `res/values/biometrics.xml` (the prompt's default reason) and the lines between the `// angular-lynx:biometrics` markers of `MainActivity.kt` and `app/build.gradle.kts`; the generator deletes them from the others.

## Clipboard

`NativeModules.AngularLynxClipboard` (`ClipboardModule.kt`, behind the runtime's `LynxClipboard`) copies text to `ClipboardManager` as a plain-text clip and reads the first item back as text, both on the main thread. `setString` calls back once with `{}` or `{ error }`, `getString` with `{ value }`, `""` when the clipboard holds no text. Android 13 and later show the copied text in a panel of their own and have TalkBack say "Text copied", so the runtime's `LynxClipboard.confirmsCopies` tells the app not to confirm it again. Android 10 and later let only the app in front read the clipboard, and Android 12 and later tell the person when it does. iOS's `ClipboardModule.swift` uses `UIPasteboard.general`.

## Haptics

`NativeModules.AngularLynxHaptics` (`HapticsModule.kt`, behind the runtime's `LynxHaptics`) plays feedback with `View.performHapticFeedback()` on the activity's window, which `MainActivity` passes as the module's param. Unlike `Vibrator`, it needs no `VIBRATE` permission and plays nothing when the person has turned touch feedback off. `impact` plays `KEYBOARD_TAP` for `light` and `soft`, `VIRTUAL_KEY` for `medium` and `rigid` and `LONG_PRESS` for `heavy`; `selection` plays `CLOCK_TICK`; `notification` plays `CONFIRM` for `success` and `REJECT` for `warning` and `error` from Android 11, and `VIRTUAL_KEY` and `LONG_PRESS` before. Each calls back once with `{}`. iOS's `HapticsModule.swift` uses UIKit's feedback generators.

## Photo picker

`NativeModules.AngularLynxImagePicker.pick(options, callback)` (`ImagePickerModule.kt`, behind the runtime's `LynxImagePicker`) has the activity open the Photo Picker (`ActivityResultContracts.PickVisualMedia`, images only), which needs no permission. `MainActivity` registers the launcher as a property, so it's registered as the activity is created, before it starts, as `ActivityResult` launchers must be; the module gets the activity's `ImagePickerModule.Host` as its param. A manifest entry (`com.google.android.gms.metadata.ModuleDependencies`) lets Google Play services install the picker on Android 10 and older, which otherwise open the document picker.

The module reads the picked photo on a background thread and calls back once with `{ base64, name, type }`, `{ canceled: true }` or `{ error, message }`. A JPEG, PNG, GIF or WebP goes back as it is unless the app passed `maxDimension` or `quality`; otherwise it's decoded with `BitmapFactory` at the smallest power-of-two reduction that covers the target, scaled, turned upright by its EXIF orientation (AndroidX `ExifInterface`, since `BitmapFactory` ignores it), drawn over white if it has transparency and compressed as a JPEG. iOS's `ImagePickerModule.swift` does the same with `PHPickerViewController` and ImageIO.

`NativeModules.AngularLynxBarcodeScanner.scan({ formats }, callback)` (`BarcodeScannerModule.kt`, behind the runtime's `LynxBarcodeScanner`) opens Google's code scanner (`GmsBarcodeScanning`) over the activity, which it gets as its param. The scanner runs in Google Play services, which shows the camera and hands back only the code, so the app declares no camera permission for it. It calls back once with `{ format, value }` or `{ error, message }`: `canceled`, `unavailable` on a phone without Play services or before Play services has downloaded the scanner, `denied` when the person refused Play services the camera, or `failed`. Only an app whose angular.json sets `permissions.camera` has the file and its library: the generator deletes both from every other app, and `MainActivity` looks the class up by name (`Class.forName`), so it builds either way. iOS's `BarcodeScannerModule.swift` reports the same results through VisionKit's `DataScannerViewController`.

## Share sheet

`NativeModules.AngularLynxFilePicker` (`FilePickerModule.kt`, behind the runtime's `LynxFilePicker`) has `pick(options, callback)`, which opens `ACTION_OPEN_DOCUMENT` (`CATEGORY_OPENABLE`, the MIME types as `EXTRA_MIME_TYPES`, extensions looked up in `MimeTypeMap`, `EXTRA_ALLOW_MULTIPLE`), checks the documents' `OpenableColumns.SIZE` against `maxBytes` and reads them on a background thread, and `save(file, callback)`, which opens `ACTION_CREATE_DOCUMENT` with the file's type and name and writes it to the URI chosen. `MainActivity` launches both through one `StartActivityForResult` launcher it registers as it's created, passed to the module as its `Host`. Neither needs a permission. Only an app whose angular.json sets `filePicker` has the module: otherwise the generator deletes it and the lines between `MainActivity.kt`'s `// angular-lynx:file-picker` markers. iOS's `FilePickerModule.swift` uses `UIDocumentPickerViewController`.

`NativeModules.AngularLynxShare.share(request, callback)` (`ShareModule.kt`, behind the runtime's `LynxShare`) writes the request's files (base64) under the cache's `angular-lynx-share/` folder, on a background thread, and opens an `ACTION_SEND` or `ACTION_SEND_MULTIPLE` chooser with their content:// URIs. They come from the manifest's `androidx.core.content.FileProvider` (authority `<applicationId>.angularlynx.share`, paths in `res/xml/share_paths.xml`), and the intent's `ClipData` and `FLAG_GRANT_READ_URI_PERMISSION` let the app picked read them. `MainActivity` registers it with itself as the param, since the module starts the chooser from it and watches its lifecycle. Android doesn't say whether sharing finished, so the module calls back `{ shared: true }` when the chooser's `IntentSender` reports the app picked, and `{ shared: false }` when the activity resumes without a pick. The last share's files stay until the next one, since the app picked may read them after the chooser closes. iOS's `ShareModule.swift` opens `UIActivityViewController` with the files as temporary files of their names, and leaves out Save Image when Info.plist has no `NSPhotoLibraryAddUsageDescription`.

`NativeModules.AngularLynxStoreReview.request(callback)` (`StoreReviewModule.kt`, behind the runtime's `LynxStoreReview`) creates a `ReviewManager` with Google Play's In-App Review API (`com.google.android.play:review`), asks it for a review flow and launches the flow over the activity, which `MainActivity` passes as the module's param, then calls back `{}`. Play shows the prompt only once the account has installed the app from Play (an internal test track or internal app sharing will do), within a quota, and fails without a Play Store, so a failed request is logged and calls back `{}` too. Only an app whose angular.json sets `storeReview` has the module: otherwise the generator deletes it and the lines between the `// angular-lynx:store-review` markers in `MainActivity.kt` and `app/build.gradle.kts`. iOS's `StoreReviewModule.swift` uses StoreKit's `requestReview(in:)`.

`NativeModules.AngularLynxCalendar.addEvent(event, callback)` (`CalendarModule.kt`, behind the runtime's `LynxCalendar`) starts `ACTION_INSERT` on `CalendarContract.Events` with the event's title, times (an all-day event's as the UTC midnights of its first day and of the day after its last, as the calendar provider stores them), all-day flag, location and notes as extras, so the calendar app opens its own editor and saves the event: the app needs no calendar permission. `MainActivity` registers a `StartActivityForResult` launcher as it's created and passes the module a `CalendarModule.Host` that launches it. The module calls back `{ result: "saved" }` when the calendar app answers `RESULT_OK`, `{ result: "unknown" }` for anything else (Google Calendar answers `RESULT_CANCELED` whether or not the event was saved), and `{ error: "unavailable" }` when no app takes the intent. Only an app whose angular.json sets `calendar` has the module: otherwise the generator deletes it and the lines between the `// angular-lynx:calendar` markers in `MainActivity.kt`.

`NativeModules.AngularLynxNfc` (`NfcModule.kt`, behind the runtime's `LynxNfc`) runs `NfcAdapter.enableReaderMode` over `MainActivity`, which Android pauses with the activity and starts again when it's back: `start` turns it on (or answers `unsupported` without an adapter, `disabled` when NFC is off), `next` calls back with the next tag it read (through `Ndef`, or an empty, writable tag for one `NdefFormatable` reports) or wrote to, and `stop` turns it off. Records cross with their bytes in base64, and the runtime builds and reads them. Only an app with angular.json's `permissions.nfc` has the module, the `NFC` permission and the not-required `android.hardware.nfc` feature, and the lines between `MainActivity.kt`'s `// angular-lynx:nfc` markers; the generator deletes them from the others.

## Canvas and WebGL

`<canvas>` (issue #211) is the shell's: `CanvasUI.kt`, a `TextureView` registered as the `canvas` element (`addBehavior(CanvasUI.behavior())`), and `WebGLModule.kt`, the `AngularLynxWebGL` module the runtime's WebGL2 context sends its calls to. `MainActivity` turns on main-thread modules (`setEnableMTSModule(true)`), so the runtime, which runs on Lynx's main thread, calls the module synchronously with `lynx.module(name)`, on Lynx's engine thread, which `MainActivity` runs off the UI thread (`setThreadStrategyForRendering(ThreadStrategyForRendering.MOST_ON_TASM)`). The canvas's `TextureView` reports its surface on the UI thread, so `WebGLContext` and `CanvasRegistry` are locked: each call makes the EGL context current and puts back what was current before, so either thread can make the next one, and a surface callback waits for a batch to end. Each context (`WebGLContext.kt`) is an EGL context with OpenGL ES 3.0 and an offscreen default framebuffer, which `present` copies into the canvas's surface; `WebGLOps.kt` is generated from the runtime's opcodes (`npm run generate:webgl-ops -w packages/native`). `encodeImage`, behind `canvas.toBlob()` and `toDataURL()`, reads the default framebuffer and compresses it with `Bitmap.compress`, returning the file as base64. The module also has the runtime's 2D context (`create2D`, `run2D`, `destroy2D`, `encode2D`): `Canvas2DContext.kt` draws into an `ARGB_8888` bitmap with `android.graphics.Canvas` and shows it in the canvas's surface with `lockHardwareCanvas()`; `Canvas2DOps.kt` is generated with the WebGL opcodes. `AssetsModule.kt` (`AngularLynxAssets`) reads a file the app bundles for the main thread's `fetch`, which has no page URL to resolve `/static/...` against.

Android's GLES has no 2D uploads from a `PIXEL_UNPACK_BUFFER` and no `glGetVertexAttribPointerv`, so those log a warning and answer 0.

## Global props

`MainActivity.globalProps()` sends what the runtime reads and Lynx has no API for (see the package README), again on every configuration change and accessibility setting change.

- **Dynamic color.** On Android 12 and later, `dynamicColors` carries the wallpaper's colors as Material 3's color roles, light and dark, as hex colors such as `#6750a4` (`DynamicColors.kt`, read by `LynxTheme.dynamicColors`). Android 14 has a color resource for most roles, which follows its contrast setting; on Android 12 and 13 each role takes its tone from the five tonal palettes, as Material Components does (a palette's own shade, or tone 40 moved to the tone with `ColorStateList.withLStar`). On the Android 14 emulator the two agree to within a few levels on the surfaces and exactly elsewhere.
- **A new wallpaper doesn't restart the activity.** Android applies the new colors as a configuration change, which `onConfigurationChanged` handles like a dark mode switch, so the running app restyles with its state intact.
- **The window follows dark mode by hand.** `configChanges` keeps the activity through a dark mode switch, so the window keeps the theme it started with. `onConfigurationChanged` sets its background (`@color/window_background`, which shows behind the system bars) and the bars' icons (`enableEdgeToEdge()`) again.
