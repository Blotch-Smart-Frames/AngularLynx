# Routing

Router providers, the stack outlet that moves between screens as native apps do, and the in-memory location classes that let Angular Router run on Lynx. `import { provideRouter, LynxStackOutlet, LynxStackPage, LynxStackChrome, LynxStackBottomBar, LynxLocationStrategy, LynxPlatformLocation, LynxRouteReuseStrategy, LynxRouterLinkActive } from '@blotch/angular-lynx';`

## Usage

```typescript title="src/app/app.config.ts"
import {
  type ApplicationConfig,
  provideZonelessChangeDetection,
} from '@angular/core';
import { withComponentInputBinding } from '@angular/router';
import { provideRenderer, provideRouter } from '@blotch/angular-lynx';
import { routes } from './app.routes';

export const appConfig: ApplicationConfig = {
  providers: [
    provideZonelessChangeDetection(),
    provideRenderer(),
    provideRouter(routes, withComponentInputBinding()),
  ],
};
```

Import `provideRouter` from `@blotch/angular-lynx`, not `@angular/router`. Everything else, such as `RouterOutlet`, `RouterLink`, `RouterLinkActive`, `Router` and `ActivatedRoute`, still comes from `@angular/router`. `RouterLink` works on any Lynx element: AngularLynx delivers a tap to its `click` listener.

## API

### `provideRouter()`

```typescript
function provideRouter(
  routes: Routes,
  ...features: RouterFeatures[]
): EnvironmentProviders;
```

Calls Angular's `provideRouter()` with your routes and features, and adds the Lynx pieces:

| Provides           | As                                                            | Why                                         |
| ------------------ | ------------------------------------------------------------- | ------------------------------------------- |
| `PlatformLocation` | `LynxPlatformLocation`                                        | Lynx has no URL bar and no browser history. |
| `LocationStrategy` | `LynxLocationStrategy`                                        | History lives in memory instead.            |
| Router config      | `withRouterConfig({ resolveNavigationPromiseOnError: true })` | A failed navigation can't crash the thread. |

- **Leaving a route destroys its components,** as on the web: `provideRouter()` keeps Angular's own `RouteReuseStrategy`. To keep route views alive instead, provide [`LynxRouteReuseStrategy`](#lynxroutereusestrategy).
- **Failed navigations** resolve to `false` instead of rejecting. Watch `Router.events` for `NavigationError` to detect them.
- **Your own `withRouterConfig()`** replaces this one, so include `resolveNavigationPromiseOnError: true` in it.
- **From an event handler,** call `router.navigate()` directly, as on the web.
- **It also tells `LynxRouterLinkActive`** where to find an element's `RouterLinkActive`, so that `LYNX_ELEMENTS` doesn't import the router itself. Without `provideRouter()`, active links don't get the `selected` trait.
- **The Android back button** calls `Location.back()` while `LynxLocationStrategy.canGoBack()` is `true`, and leaves the app when it's `false`. It works in the Android app `ng build --platform android` makes, and in [your own app](/guide/embedding/#connect-the-android-back-button) if it sends the same event. With a `LocationStrategy` of your own, the back button always leaves the app.

### `LynxStackOutlet`

```typescript
@Component({ selector: 'lynx-stack-outlet', exportAs: 'outlet' })
class LynxStackOutlet extends RouterOutlet {
  readonly animation: InputSignal<StackAnimation | undefined>;
  readonly swipeBack: InputSignalWithTransform<boolean, unknown>;
  readonly pageClass: InputSignal<string>;
  readonly hideBottomBar: InputSignal<StackBottomBarDefault>;
}

type StackAnimation = 'ios' | 'material' | 'none';
type StackBottomBarDefault = 'pushed' | 'never';
```

A `RouterOutlet` that keeps a stack of screens and moves between them as iOS and Android apps do, with a swipe back. Use it in place of `<router-outlet>`: it has the same inputs, outputs and API, and the screens under the top one stay alive. See [Slide screens in and out](/guide/routing#slide-screens-in-and-out-as-a-native-app-does) for what it does, and which way each navigation moves.

| Input           | Default                                    | What it does                                                                                                                       |
| --------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| `animation`     | `'material'` on Android, `'ios'` elsewhere | How screens move. `'none'` swaps them at once and turns the swipe off.                                                             |
| `swipeBack`     | `true`                                     | Whether a finger dragging the top screen to the right takes it back: from the left edge, or anywhere that doesn't scroll sideways. |
| `pageClass`     | `''`                                       | Classes for each screen's frame. Without them a screen is drawn on `var(--background, #ffffff)`.                                   |
| `hideBottomBar` | `'pushed'`                                 | Which screens take the app's tab bar or dock away when their route doesn't say: every screen pushed over the first, or `'never'`.  |

- **It fills its parent** (`flex: 1`) and clips the screens in it. Each screen sits in a frame of its own, absolutely placed over the others.
- **While Reduce Motion is on,** a push or a pop cross-fades.
- **A swipe goes back through the history,** to the entry before the top screen's, however many it added since. A guard that refuses brings the screen back.
- **A screen pushed over the first takes the bottom bar away,** and says so through [`LynxStackChrome`](#lynxstackchrome). A route's `data: { bottomBar: 'visible' | 'hidden' }` says otherwise for its screen.

### `StackNavigationInfo`

```typescript
type StackNavigationInfo = {
  readonly stack?: 'push' | 'pop' | 'root';
};
```

What a navigation does to a `LynxStackOutlet`'s stack, when the URL doesn't say it the way you want. Pass it as the navigation's `info`: `[info]="{ stack: 'push' }"` on a `routerLink`, or `router.navigate(commands, { info: { stack: 'root' } })`.

| `stack`  | The stack                                                                   |
| -------- | --------------------------------------------------------------------------- |
| `'push'` | Pushes the screen, sliding it in, even at the same depth or already in it.  |
| `'pop'`  | Pops back to the screen. One that isn't in the stack slides in from behind. |
| `'root'` | Starts a new stack with the screen, without a transition.                   |

### `LynxStackPage`

```typescript
class LynxStackPage {
  readonly active: Signal<boolean>;
  readonly bottomBarHidden: Signal<boolean>;
}
```

The screen of a `LynxStackOutlet` that a component is on, which any component on it can inject (`inject(LynxStackPage, { optional: true })`, null off a stack). `active()` is `true` while the screen is on top, and `false` while another covers it or it's on its way out: a covered screen's components keep running, so pause what only matters while it shows. It also identifies the screen, for state kept per screen.

`bottomBarHidden()` is `true` when the screen takes the bottom bar away while it's on top (see [`LynxStackChrome`](#lynxstackchrome)). It doesn't change while the screen is covered, so a screen can drop the room it keeps at its end for the bar without moving its content under a screen on top.

### `LynxStackChrome`

```typescript
@Injectable({ providedIn: 'root' })
class LynxStackChrome {
  readonly bottomBarHidden: Signal<boolean>;
  readonly bottomBarProgress: Signal<number>;
  readonly bottomBarMotion: Signal<StackBarMotion>;
}

type StackBarMotion = {
  readonly animation: 'ios' | 'material' | 'fade' | 'none';
  readonly duration: number;
  readonly easing: string;
  readonly coveredX: number;
};

type StackBottomBar = 'visible' | 'hidden';
```

What the stack that's showing does, for a bar outside it: a tab bar or a dock beside the `<router-outlet>` whose tabs hold `<lynx-stack-outlet>`s. The [Tab Bar](/dolan/tab-bar) and the [Dock](/dolan/dock) follow it through [`LynxStackBottomBar`](#lynxstackbottombar), which also has the screen underneath carry the bar on iOS. A bar of your own can do the same, or read the chrome directly and slide away on its own, as below.

| Signal              | What it says                                                                                                                                                                                                                                                                                              |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `bottomBarHidden`   | Whether the bar should be away: the screen on top takes it away. It changes as a push or a pop starts, and when the router goes back after a swipe, not while a finger drags. Hide the bar from screen readers and taps while it's `true`.                                                                |
| `bottomBarProgress` | How far the bar is away, `0` (shown) to `1` (gone). It follows a finger dragging a screen back move by move. A push or a pop sets it to where the bar ends up as the screens start to move.                                                                                                               |
| `bottomBarMotion`   | How the bar gets there: the screens' `animation` (`'fade'` while Reduce Motion cross-fades them), and the `duration` (ms) and `easing` of the push or pop, `0` while a finger drags or nothing moves. `coveredX` is how far the screen under a pushed one moves, as a share of the width (`-0.3` on iOS). |

```typescript
@Component({
  selector: 'app-player-bar',
  host: {
    '[style.transform]': 'transform()',
    '[style.transition]': 'transition()',
  },
  template: `…`,
})
export class PlayerBar {
  readonly #chrome = inject(LynxStackChrome);
  protected readonly transform = computed(
    () => `translateY(${this.#chrome.bottomBarProgress() * 100}%)`,
  );
  protected readonly transition = computed(() => {
    const { duration, easing } = this.#chrome.bottomBarMotion();
    return duration > 0 ? `transform ${duration}ms ${easing}` : 'none';
  });
}
```

- **Which screens take the bar away:** every screen pushed over a stack's first one, unless its outlet's `hideBottomBar` is `'never'`. A route says otherwise in its data: `{ path: 'results', component: Results, data: { bottomBar: 'visible' } }` keeps it, and `bottomBar: 'hidden'` takes it away even from a stack's first screen.
- **Only a stack the app shows counts:** one with a screen the router has active, on screens that are on top of their own stacks. A tab the router has left doesn't hide the bar on another tab, nor does a stack on a covered screen.
- **Stacks inside stacks:** the innermost decides. A screen that doesn't say (a stack's first, or a pushed one under `hideBottomBar="never"`) leaves the bar as the stacks around it have it.
- **On a stack's screen, it follows only the stacks on that screen.** A bar inside a screen moves with the screen, so the stack that moves the screen doesn't move the bar too.

### `LynxStackBottomBar`

```typescript
@Directive({ selector: '[lynxStackBottomBar]', exportAs: 'lynxStackBottomBar' })
class LynxStackBottomBar {
  readonly carried: Signal<boolean>;
  readonly hidden: Signal<boolean>;
  readonly progress: Signal<number>;
  readonly motion: Signal<StackBarMotion>;
}
```

Makes a bottom bar part of the screen that has it while a stack's screens move as iOS's do, as UIKit puts its tab bar in the view of the screen that has it while a navigation controller moves. The screen pushed over it then covers the bar as it covers the screen underneath, with its rounded corner and its shadow, the dark over the screen underneath dims the bar too, and the bar moves with that screen under a finger. A bar outside the stack would lie over both screens, so the best it could do is cut itself off along the pushed screen's edge. The [Tab Bar](/dolan/tab-bar) and the [Dock](/dolan/dock) put it on their hosts.

Put it on your bar's host, and move the bar with its signals rather than [`LynxStackChrome`](#lynxstackchrome)'s:

```typescript
@Component({
  selector: 'app-player-bar',
  hostDirectives: [LynxStackBottomBar],
  host: {
    '[style.transform]': 'transform()',
    '[style.transition]': 'transition()',
  },
  template: `…`,
})
export class PlayerBar {
  readonly #bar = inject(LynxStackBottomBar);
  protected readonly transform = computed(
    () => `translateY(${this.#bar.progress() * 100}%)`,
  );
  protected readonly transition = computed(() => {
    const { duration, easing } = this.#bar.motion();
    return duration > 0 ? `transform ${duration}ms ${easing}` : 'none';
  });
}
```

| Signal     | What it says                                                                                                        |
| ---------- | ------------------------------------------------------------------------------------------------------------------- |
| `carried`  | Whether a screen carries the bar now: the bar is in that screen, along its bottom, at rest, and moves with it.      |
| `hidden`   | The chrome's `bottomBarHidden`. Hide the bar from screen readers and taps while it's `true`.                        |
| `progress` | The chrome's `bottomBarProgress`, or `0` while a screen carries the bar, which should then look as it does at rest. |
| `motion`   | The chrome's `bottomBarMotion`, with a `duration` of `0` while a screen carries the bar.                            |

- **Which screen carries it:** the one that shows the bar, as another screen moves over it or off it. A push carries it in the screen underneath, and a pop or a swipe back carries it back in. That screen keeps it while it's covered, and the bar goes back to its own place once that screen is on top again, or the router leaves the stack (another tab).
- **Where it doesn't:** a screen that's popped, or one a finger drags (which may go), doesn't carry a bar it shows: the bar slides away on its own. Neither does Android's motion, nor the cross-fade under Reduce Motion: `progress` and `motion` are then the chrome's.
- **Where it sits:** absolutely, along the bottom and across the width of the screen carrying it, which fills the stack. So the stack should run to the bottom of the screen, as it does beside a floating dock, or once a tab bar is out of the layout (the Tab Bar lies over the stack while it's away or on its way).
- **Its place:** a comment holds the bar's place in its parent meanwhile, as with CDK's `DomPortal`.

### `LynxRouterLinkActive`

```typescript
@Directive({ selector: '[routerLinkActive]' })
class LynxRouterLinkActive {}
```

Adds the `selected` accessibility trait to an element while Angular's `RouterLinkActive` on it says its route is active, and takes it away after, so screen readers know which link is the current one. It's part of `LYNX_ELEMENTS`, so it's on every `routerLinkActive` element of a component that imports `LYNX_ELEMENTS` and `RouterLinkActive`. It has no inputs or outputs of its own.

- **It keeps the element's own traits.** `accessibility-traits="button"` reads `button,selected` while the link is active, and `button` again after. A trait set later is merged the same way.
- **Android leaves the element's traits alone.** It reads a single trait, `none`, `image` or `button`, and has no selected trait, so a list would only lose the element's own.
- **On a component's host**, add it to `hostDirectives` next to `RouterLinkActive`. Host directives don't match selectors, so `LYNX_ELEMENTS` can't add it there:

```typescript title="src/app/tab.ts"
import { Component, input } from '@angular/core';
import { RouterLink, RouterLinkActive } from '@angular/router';
import { LYNX_ELEMENTS, LynxRouterLinkActive } from '@blotch/angular-lynx';

@Component({
  selector: 'app-tab',
  imports: [LYNX_ELEMENTS],
  hostDirectives: [
    { directive: RouterLink, inputs: ['routerLink: route'] },
    {
      directive: RouterLinkActive,
      inputs: ['routerLinkActive: activeClass'],
    },
    LynxRouterLinkActive,
  ],
  host: { 'accessibility-traits': 'button' },
  template: `<text><ng-content /></text>`,
})
export class Tab {
  readonly route = input.required<string>();
}
```

### `LynxRouteReuseStrategy`

```typescript
@Injectable()
class LynxRouteReuseStrategy implements RouteReuseStrategy {}
```

Keeps each route's component alive when you navigate away, and reattaches it when you come back. `provideRouter()` doesn't install it. Provide it after `provideRouter()` to opt in:

```typescript title="src/app/app.config.ts"
import { RouteReuseStrategy } from '@angular/router';
import { LynxRouteReuseStrategy, provideRouter } from '@blotch/angular-lynx';

export const appConfig: ApplicationConfig = {
  providers: [
    provideRouter(routes),
    { provide: RouteReuseStrategy, useClass: LynxRouteReuseStrategy },
  ],
};
```

- `ngOnDestroy` doesn't run when you leave a route, and component state survives.
- Views are stored by route path, so `/user/1` and `/user/2` share one stored view.
- Nothing is ever evicted: every route you visit stays in memory.
- It doesn't save native elements. A reattached route rebuilds its elements, as a new one creates them. See [Renderer internals](/guide/renderer-architecture#route-views).

### `LynxRouteReuseStrategy.shouldDetach()`

```typescript
shouldDetach(route: ActivatedRouteSnapshot): boolean;
```

Always returns `true`.

### `LynxRouteReuseStrategy.store()`

```typescript
store(route: ActivatedRouteSnapshot, handle: DetachedRouteHandle | null): void;
```

Stores the view under the route's path, or forgets it when `handle` is `null`.

### `LynxRouteReuseStrategy.shouldAttach()`

```typescript
shouldAttach(route: ActivatedRouteSnapshot): boolean;
```

Returns `true` when a view is stored for the route's path.

### `LynxRouteReuseStrategy.retrieve()`

```typescript
retrieve(route: ActivatedRouteSnapshot): DetachedRouteHandle | null;
```

Returns the stored view, or `null`.

### `LynxRouteReuseStrategy.shouldReuseRoute()`

```typescript
shouldReuseRoute(future: ActivatedRouteSnapshot, curr: ActivatedRouteSnapshot): boolean;
```

Returns `true` when both snapshots come from the same route config, as Angular's default does.

### `LynxLocationStrategy`

```typescript
@Injectable()
class LynxLocationStrategy extends LocationStrategy {}
```

A `LocationStrategy` that keeps a history stack in memory, starting at `/`. Angular's `Location` service calls it, so you rarely call it yourself.

### `LynxLocationStrategy.path()`

```typescript
path(): string;
```

Returns the current URL, including its query string.

### `LynxLocationStrategy.prepareExternalUrl()`

```typescript
prepareExternalUrl(internal: string): string;
```

Returns `internal` unchanged.

### `LynxLocationStrategy.getBaseHref()`

```typescript
getBaseHref(): string;
```

Always returns `'/'`.

### `LynxLocationStrategy.getState()`

```typescript
getState(): unknown;
```

Returns the current entry's state, or `null`.

### `LynxLocationStrategy.pushState()`

```typescript
pushState(state: unknown, title: string, url: string, queryParams: string): void;
```

Adds a history entry and drops any forward entries.

### `LynxLocationStrategy.replaceState()`

```typescript
replaceState(state: unknown, title: string, url: string, queryParams: string): void;
```

Replaces the current history entry.

### `LynxLocationStrategy.back()` and `forward()`

```typescript
back(): void;
forward(): void;
```

Same as `historyGo(-1)` and `historyGo(1)`.

### `LynxLocationStrategy.canGoBack`

```typescript
readonly canGoBack: Signal<boolean>;
```

`true` when there's an entry before the current one, so `back()` goes somewhere. A replaced entry doesn't count.

### `LynxLocationStrategy.historyGo()`

```typescript
historyGo(relativePosition?: number): void;
```

Moves through history and notifies `popstate` listeners. A move past either end does nothing.

### `LynxLocationStrategy.historyIndex`

```typescript
get historyIndex(): number;
```

Where the current entry is in the history, from `0` for the first. `LynxStackOutlet` keeps each screen's, so its swipe goes back to the entry before the screen's.

### `LynxLocationStrategy.onPopState()`

```typescript
onPopState(fn: LocationChangeListener): VoidFunction;
```

Adds a `popstate` listener. Call the returned function to remove it.

### `LynxPlatformLocation`

```typescript
@Injectable()
class LynxPlatformLocation extends PlatformLocation {}
```

A `PlatformLocation` with its own in-memory history. It parses URLs by hand, because the Lynx JavaScript environment has no `URL` class.

### `LynxPlatformLocation.href`

```typescript
get href(): string;
```

The current URL as `lynx://app` followed by its path, query string and fragment.

### `LynxPlatformLocation.protocol`, `hostname` and `port`

```typescript
get protocol(): string; // 'lynx:'
get hostname(): string; // 'app'
get port(): string; // ''
```

Fixed values, because there's no real server.

### `LynxPlatformLocation.pathname`, `search` and `hash`

```typescript
get pathname(): string;
get search(): string;
get hash(): string;
```

Parts of the current URL. `pathname` is `'/'` when empty. `search` keeps its `?` and `hash` keeps its `#`, or each is `''`.

### `LynxPlatformLocation.getBaseHrefFromDOM()`

```typescript
getBaseHrefFromDOM(): string;
```

Always returns `'/'`.

### `LynxPlatformLocation.getState()`

```typescript
getState(): unknown;
```

Returns the current entry's state.

### `LynxPlatformLocation.pushState()` and `replaceState()`

```typescript
pushState(state: unknown, title: string, url: string): void;
replaceState(state: unknown, title: string, url: string): void;
```

Adds an entry, dropping forward entries, or replaces the current one.

### `LynxPlatformLocation.back()`, `forward()` and `historyGo()`

```typescript
back(): void;
forward(): void;
historyGo(relativePosition?: number): void;
```

Move through history and notify `popstate` listeners. A move past either end does nothing.

### `LynxPlatformLocation.onPopState()` and `onHashChange()`

```typescript
onPopState(fn: LocationChangeListener): VoidFunction;
onHashChange(fn: LocationChangeListener): VoidFunction;
```

`onPopState` adds a listener and returns its remover. `onHashChange` does nothing, because hash changes arrive as `popstate`.
