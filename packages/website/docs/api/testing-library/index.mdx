# @blotch/angular-lynx-testing-library

Renders a component through the Lynx renderer in a unit test, then finds and taps its elements with Testing Library queries that read Lynx's accessibility attributes. `import { render } from '@blotch/angular-lynx-testing-library';`

## Usage

```typescript title="src/app/counter/counter.ts"
import { Component, signal } from '@angular/core';
import { LYNX_ELEMENTS } from '@blotch/angular-lynx';

@Component({
  selector: 'app-counter',
  imports: [LYNX_ELEMENTS],
  template: `
    <view
      [accessibility-element]="true"
      accessibility-traits="button"
      accessibility-label="Add one"
      (bindtap)="increment()"
    >
      <text>Taps: {{ taps() }}</text>
    </view>
  `,
})
export class Counter {
  readonly taps = signal(0);

  increment(): void {
    this.taps.update((n) => n + 1);
  }
}
```

```typescript title="src/app/counter/counter.test.ts"
import {
  fireEvent,
  render,
  waitForUpdate,
} from '@blotch/angular-lynx-testing-library';
import { describe, expect, it } from 'vitest';

import { Counter } from './counter';

describe('Counter', () => {
  it('counts taps', async () => {
    const { getByRole, getByText } = await render(Counter);

    fireEvent.tap(getByRole('button', { name: 'Add one' }));
    await waitForUpdate();

    expect(getByText('Taps: 1')).toBeTruthy();
  });
});
```

Add the library with [`ng generate @blotch/angular-lynx:add-testing`](/api/schematics#add-testing), and run tests with `ng test`. The [unit-test builder](/api/build/#unit-test) loads the library's setup, so there's no setup file to write.

## API

### `render(component, options?)`

```typescript
function render<Q extends Queries = typeof queries, C = unknown>(
  component: Type<C>,
  options?: RenderOptions<Q, C>,
): Promise<RenderResult<Q, C>>;
```

Bootstraps `component` as a Lynx app, renders it into the test's DOM, and resolves once the first render is done.

```typescript
const { getByText, rerender } = await render(Greeting, {
  inputs: { name: 'Lynx' },
});
expect(getByText('Hello, Lynx')).toBeTruthy();

await rerender({ inputs: { name: 'Angular' } });
expect(getByText('Hello, Angular')).toBeTruthy();
```

- It first destroys the app a previous `render()` left, and clears `document.body`.
- The app gets `provideZonelessChangeDetection()`, `provideRenderer()` and your `options.providers`.
- **`options.inputs`** are set before the first change detection, as a parent template binds them. A required input has its value when the template first reads it, and `ngOnInit` sees them all.
- **`options.initialURL`** is the link that started the app, such as `myapp://orders/42`. [`LynxLinking.getInitialURL()`](/api/angular-lynx/linking#lynxlinkinggetinitialurl) returns it, and with `provideRouter()` the app's first screen is the link's route, with nothing under it. A link the router has no route for starts the app at `/`, as on a phone. Left out, `getInitialURL()` is `null`.
- Elements render under a `<page>` element, the result's `container`.
- It rejects a name that isn't one of the component's inputs, and lists the ones it has.
- Like `bootstrapApplication()`, it hides the [splash screen](/api/angular-lynx/splash-screen) once the component is rendered, unless `options.providers` has `provideSplashScreen()`. A spec reads `LynxSplashScreen.visible()` to check when the app hides it.

### `cleanup()`

```typescript
function cleanup(): void;
```

Destroys the rendered app. It runs after every test, so you rarely call it. To turn that off, set the environment variable `ATL_SKIP_AUTO_CLEANUP=true`.

### `waitForUpdate()`

```typescript
function waitForUpdate(): Promise<void>;
```

Waits one task (a `setTimeout` of 0), so the change detection Angular scheduled can run, then runs change detection once more. Await it after `fireEvent` or after setting a signal, before you check the rendered output.

### `fireEvent(element, event)`

```typescript
fireEvent(element: Element, event: Event): boolean;
fireEvent.tap(element: Element, init?: Record<string, unknown>): boolean;
// … one method per event in the Event reference
```

Fires a Lynx event at `element`, which runs the handlers a device would, such as `(bindtap)`. The methods and their bindings are in the [Event reference](/api/testing-library/event-reference).

- **Bubbling**: touch, mouse and key events go from `element` up to the page, as on a device, so a tap on a row reaches its card's `(click)`. A `(catch*)` handler runs and stops the event there, and `(capture-*)` handlers run first, from the page down. Other events, such as `scroll` and `input`, run only `element`'s own handler.
- **`init`**: properties to set on the event. `{ detail: { value: 'hi' } }` arrives as `$event.detail.value`.
- **`init.bubbles`**: overrides whether the event goes up to the page. `{ bubbles: false }` keeps a tap on `element`.
- **`init.eventType`**: fires at one kind of handler on `element` alone, such as `'catchEvent'` for its `(catch*)` handler.
- **`event`**: an event of type `'<eventType>:<name>'`, such as `new Event('bindEvent:change')`, for an event without a method. A `CustomEvent`'s `detail` arrives as `$event.detail`.

**`fireEvent` doesn't render.** The handler runs before `fireEvent` returns, so a spy or a signal you read directly already shows the change. Angular renders the result in a change detection it schedules for after the current task. Await `waitForUpdate()` before checking the rendered output.

### `eventMap`

```typescript
const eventMap: Record<string, { defaultInit: { bubbles?: boolean } }>;
```

The events that `fireEvent` has a method for, keyed by event name. `defaultInit.bubbles` is `true` for the events that go up to the page.

### `openedURLs()`

```typescript
function openedURLs(): readonly OpenedURL[];

type OpenedURL = { readonly url: string; readonly inApp: boolean };
```

The links the app opened with [`LynxLinking`](/api/angular-lynx/linking) in this test, oldest first, so a spec can check where a tap leads. `inApp` is `true` for `openInApp()` and `false` for `openURL()`. Under the testing library, both resolve without opening anything, and `canOpenURL()` resolves `true`. Each test starts with none.

```typescript
fireEvent.tap(screen.getByText('Help'));
await waitForUpdate();

expect(openedURLs()).toEqual([
  { url: 'https://example.com/help', inApp: true },
]);
```

### `runShortcut()`

```typescript
function runShortcut(id: string, options?: { readonly route?: string }): void;
```

Runs one of the app's [shortcuts](/guide/shortcuts), as the person does by asking Siri or from the app icon's menu, so a spec can check what the app does with it. A spec doesn't read angular.json, so `id` only has to be one the code under test handles with [`LynxShortcuts.on()`](/api/angular-lynx/shortcuts#lynxshortcutson), and a shortcut that has a `route` there gets it in `options`, which the router then navigates to. The shortcut reaches the app as it does on a phone, through the background thread, so wait for it with `waitForUpdate()`. Run before the app has injected `LynxShortcuts`, it waits, as the shortcut that starts an app does. Each test starts with none waiting.

```typescript
await render(Feed);

runShortcut('refresh');
await waitForUpdate();

expect(screen.getByText('Refreshed')).toBeInTheDocument();
```

### `queueBarcodeScan()`

```typescript
function queueBarcodeScan(scan: {
  readonly format: string;
  readonly value: string;
}): void;
function cancelBarcodeScan(): void;
function failBarcodeScan(
  code: 'unavailable' | 'denied' | 'failed',
  message?: string,
): void;
```

Answers a [`LynxBarcodeScanner.scan()`](/api/angular-lynx/barcode-scanner), since a spec has no camera to point. A scan stays open until one of these answers it:

- **`queueBarcodeScan()`** reads `scan`, as if the person pointed the camera at it: `scan()` resolves with it.
- **`cancelBarcodeScan()`** closes the scanner, as the Cancel button does: `scan()` rejects with `canceled`.
- **`failBarcodeScan()`** rejects with `code`, such as `denied` for a person who won't let the app use the camera.

Each call answers the open scan, or, when none is open, the next one as soon as it's called, in order. The answer reaches the app through the background thread, as on a phone, so wait for it with `waitForUpdate()`. Each test starts with no scan open and nothing queued.

```typescript
await render(CheckIn);

queueBarcodeScan({ format: 'qr', value: 'TICKET-42' });
fireEvent.tap(screen.getByText('Scan ticket'));
await waitForUpdate();

expect(screen.getByText('Welcome, ticket 42')).toBeInTheDocument();
```

### `pressBackButton()`

```typescript
function pressBackButton(): boolean;
```

Presses Android's back button, so a spec can check what the app does with it: close what's open on top (a handler registered with [`LynxBackButton.on()`](/api/angular-lynx/back-button#lynxbackbuttonon)), or go back a screen through the router. As on Android, the press reaches the app only while the app takes back; otherwise Android would leave the app, and it returns `false`. The press reaches the app as it does on a phone, through the background thread, so wait for it with `waitForUpdate()`. Each test starts with back left to Android. An `<overlay>` takes back before the app on a phone: fire its `requestclose` event for that instead.

```typescript
await render(Search);
fireEvent.tap(screen.getByText('Search'));
await waitForUpdate();

expect(pressBackButton()).toBe(true);
await waitForUpdate();

expect(screen.queryByText('Results')).toBeNull();
```

### `openLink()`

```typescript
function openLink(url: string): void;
```

Opens the app with a link, as the person does by tapping a link with one of angular.json's [`deepLinkSchemes`](/guide/deep-links) while the app is open, so a spec can check where it leads. With `provideRouter()`, the router navigates to the link's route, and each [`LynxLinking.onURL()`](/api/angular-lynx/linking#lynxlinkingonurl) handler is called with the URL. The link reaches the app as it does on a phone, through the background thread, so wait for it with `waitForUpdate()`. Sent before the app listens, it waits for the first handler, as a link that arrives while an app starts does. It's never the link that started the app: `getInitialURL()` stays `null`. Give that one to `render()` as [`initialURL`](#rendercomponent-options). Each test starts with none waiting.

```typescript
await render(App, { providers: [provideRouter(routes)] });

openLink('myapp://orders/42');
await waitForUpdate();

expect(screen.getByText('Order 42')).toBeInTheDocument();
```

### `addBluetoothDevice()`

```typescript
function addBluetoothDevice(
  device: FakeBluetoothDevice,
): FakeBluetoothDeviceRef;
```

Puts a Bluetooth LE device in range of the app, for [`LynxBluetooth`](/api/angular-lynx/bluetooth) to find, connect to and talk to as it would a real one. A scan that's running sees it at once, and one that starts later sees it as it starts. A device advertises every service it has unless `advertisedServices` says otherwise, and a characteristic can be read, written and notified unless its `properties` say otherwise. `onWrite` is called with each value the app writes and the device, so the spec can answer as the real device does. A write longer than the device takes is refused, as on a phone: `maxWriteLength` sets the limit without a response. Each test starts with no devices and the radio on, and adding an `id` a second time throws.

```typescript
const frame = addBluetoothDevice({
  id: 'frame',
  name: 'Blotch - XyZ1',
  services: {
    [SETUP]: {
      [CREDENTIALS]: {
        properties: ['write'],
        onWrite: (_value, device) => device.notify(SETUP, STATUS, ONLINE),
      },
      [STATUS]: { properties: ['notify'] },
    },
  },
});
await render(SetUpFrame);

fireEvent.tap(await screen.findByText('Blotch - XyZ1'));
await waitForUpdate();

expect(frame.writes).toEqual([
  {
    service: SETUP,
    characteristic: CREDENTIALS,
    value: WIFI,
    withResponse: true,
  },
]);
```

The device it returns has `connected`, `writes` (what the app wrote, oldest first), `notify(service, characteristic, value)`, which reaches the app while it's subscribed, and `disconnect()`, which ends the connection from the device's side, as going out of range does. UUIDs are spelled either way, as [`canonicalBluetoothUUID()`](/api/angular-lynx/bluetooth#canonicalbluetoothuuid) reads them.

### `setBluetoothState()`

```typescript
function setBluetoothState(state: BluetoothState): void;
```

Sets the state of the phone's Bluetooth, as the person turning it off or refusing permission does, so a spec can check what the app shows then. Anything but `'poweredOn'` ends a running scan and every connection, as it does on a phone. `'unknown'` stands for not asked yet: the person allows it when `LynxBluetooth` asks, as `requestPermission()`, `scan()` and `connect()` do.

```typescript
setBluetoothState('poweredOff');
await render(SetUpFrame);

expect(await screen.findByText('Turn on Bluetooth')).toBeInTheDocument();
```

### `setAppState()`

```typescript
function setAppState(state: 'active' | 'inactive' | 'background'): void;
```

Sends the app to the background, or brings it back, as the person does by leaving the app and coming back to it, so a spec can check what the app does on its return. [`LynxAppState.state()`](/api/angular-lynx/app-state) becomes `state`, and `active()` is `true` only for `'active'`. It reaches the app as a change to the host's global props, as on a phone, so wait for it with `waitForUpdate()`. Wait between two states too: an `effect()` runs once for both otherwise, and never sees the app leave. Each test starts `'active'`.

```typescript
await render(Schedule);

setAppState('background');
await waitForUpdate();
vi.setSystemTime(new Date('2026-01-02T09:00'));
setAppState('active');
await waitForUpdate();

expect(screen.getByText('Today: 2 January')).toBeInTheDocument();
```

### Biometrics

```typescript
function setBiometrics(phone: {
  readonly type?: BiometryType;
  readonly enrolled?: boolean;
  readonly deviceCredential?: boolean;
}): void;
function queueBiometricResult(result: 'success' | BiometricsErrorCode): void;
function biometricPrompts(): readonly {
  readonly reason: string;
  readonly allowDeviceCredential: boolean;
}[];
```

Each test starts with a phone that has **Face ID set up behind a passcode**, where every prompt succeeds. [`LynxBiometrics`](/api/angular-lynx/biometrics) and `LynxSecureStorage`'s `requireBiometrics` see it as they see the shells' module.

- **`setBiometrics()`** changes the phone. What you leave out keeps its value. `{ type: 'none' }` is a phone without a sensor, or an app without `permissions.biometrics`.
- **`queueBiometricResult()`** has the next prompt end that way, such as `'canceled'`. Results queue one per prompt; once they run out, prompts succeed.
- **`biometricPrompts()`** lists the prompts the app showed, oldest first: each `authenticate()`, and each read of a value kept behind biometrics.

```typescript
await render(Unlock);
queueBiometricResult('canceled');

fireEvent.tap(screen.getByText('Unlock'));
await waitForUpdate();

expect(screen.getByText('Still locked')).toBeInTheDocument();
expect(biometricPrompts()).toEqual([
  { reason: 'Unlock your notes', allowDeviceCredential: false },
]);
```

### `*ByAccessibilityLabel`

```typescript
getByAccessibilityLabel(label: Matcher, options?: MatcherOptions): HTMLElement;
// getAllBy…, queryBy…, queryAllBy…, findBy… and findAllBy… too
```

Finds elements by their `accessibility-label`, the text a screen reader reads for them. Testing Library's `*ByLabelText` reads `<label>` and `aria-*` attributes, which Lynx elements don't have.

- **`label`**: a string, a RegExp or a function, as for `getByText`.
- **`options`**: `exact: false` matches part of the label in any case. `normalizer` changes how whitespace is trimmed.
- **Variants**: the same six as Testing Library's queries. `findBy…` waits for the element, 1 second by default.

### `*ByRole`

```typescript
getByRole(role: ByRoleMatcher, options?: ByRoleOptions): HTMLElement;
// getAllBy…, queryBy…, queryAllBy…, findBy… and findAllBy… too
```

Testing Library's `*ByRole`, reading Lynx's accessibility attributes as a screen reader does. It finds what Testing Library finds too, such as an `<input>` as a `textbox`.

| `accessibility-traits` | Role        |
| ---------------------- | ----------- |
| `button`               | `button`    |
| `link`                 | `link`      |
| `image`                | `img`       |
| `header`               | `heading`   |
| `search`               | `searchbox` |
| `adjustable`           | `slider`    |
| `tabbar`               | `tablist`   |

- **`<image>` is an `img`** unless it sets `accessibility-traits`. Other traits, such as `text`, give no role.
- **`accessibility-heading` is a `heading`**, and an `accessibility-role-description` of `button`, `switch`, `checkbox`, `image` or `progressbar` is that role (`image` is `img`), as Android reads them. These add to the roles from the traits.
- **Only reachable elements match.** A screen reader reaches `<text>`, `<image>`, and other elements with `accessibility-element="true"`, outside `accessibility-elements-hidden`. A `tabbar` is read from the container around the tabs, so it needs no `accessibility-element`. Pass `hidden: true` to include the rest.
- **`name`** is the `accessibility-label`. A `<text>` without one is named by its text. A `<view>` isn't named by the text inside it, since iOS doesn't read it. An `accessibility-status` comes first, as iOS and Android read it: `{ name: 'Unread, Inbox' }`.
- **`selected`** is the `selected` trait: `accessibility-traits="button,selected"`, which an active `routerLinkActive` element gets, and which `[lynxAccessibilityTraits]="{ selected: true }"` adds. iOS reads a comma-separated list, but Android reads only one trait.
- **`value: { text }`** is the `accessibility-value`.
- **Other ARIA states**, such as `checked` or `expanded`, have no Lynx attribute, so a Lynx element never has them, a `switch` or `checkbox` from a role description included.

### `screen`

Every query, bound to `document.body`, with Testing Library's `debug()` and `logTestingPlaygroundURL()`.

### `within(element, queries?)`

```typescript
function within(element: HTMLElement): BoundLynxQueries;
function within<Q extends Queries>(
  element: HTMLElement,
  queries: Q,
): BoundFunctions<Q>;
```

Binds every query to `element`, to search one part of the tree. Pass `queries` to bind only those. `getQueriesForElement` is the same function.

### `queries`

```typescript
const queries: LynxQueries;
```

Every query, unbound, each taking the container first: Testing Library's, with `*ByRole` and `*ByAccessibilityLabel` from this library. Each one is also exported on its own, such as `getByAccessibilityLabel(container, 'Close')`.

`getByText` finds the element whose own text matches, as in a browser. For text written straight in a `<view>` or `<div>`, that's the plain `<text>` the runtime draws it in (see [HTML tags](/guide/elements/#html-tags)): its `parentElement` is the `<view>`.

## Types

### `RenderOptions`

```typescript
type RenderOptions<Q extends Queries = typeof queries, C = unknown> = {
  providers?: (Provider | EnvironmentProviders)[];
  queries?: Q;
  inputs?: RenderInputs<C>;
};
```

| Property    | Description                                                                                             |
| ----------- | ------------------------------------------------------------------------------------------------------- |
| `providers` | Extra providers for the test app, such as `provideRouter(routes)`                                       |
| `queries`   | Custom queries to bind to `container`, next to the library's [`queries`](#queries)                      |
| `inputs`    | Values for the component's inputs, keyed by the name a template binds. An aliased input takes its alias |

### `RenderInputs`

```typescript
type RenderInputs<C = unknown> = {
  [K in keyof C]?: InputValue<C[K]>;
} & Record<string, unknown>;
```

Each of the component's properties takes the value its input does. For `readonly count = input(0)`, `inputs: { count: 'three' }` doesn't compile. Other names are allowed too, such as `class` for `input('', { alias: 'class' })`. `render()` checks every name when the test runs.

### `RenderResult`

| Property       | Type                                             | Description                                                                       |
| -------------- | ------------------------------------------------ | --------------------------------------------------------------------------------- |
| `container`    | `Element`                                        | The `<page>` element that holds everything rendered                               |
| `componentRef` | `ComponentRef<C>`                                | The root component. Use `componentRef.injector.get(Token)` to reach a service     |
| `unmount`      | `() => void`                                     | Destroys the app, like `cleanup()`                                                |
| `rerender`     | `({ inputs }) => Promise<RenderResult>`          | Changes inputs `render()` set, keeping the component. See below                   |
| `rerender`     | `(component, options?) => Promise<RenderResult>` | Renders another component in its place                                            |
| `asFragment`   | `() => DocumentFragment`                         | A copy of `container`, for snapshot tests                                         |
| `getByText`, … | Query functions                                  | Every query in [`queries`](#queries), bound to `container`, plus your custom ones |

**`rerender({ inputs })`** sets the inputs you pass, runs change detection, and resolves when the tree shows them. The component keeps its state.

- **Inputs you leave out keep their values.** Angular has no way to put an input back to its initial value.
- **It only changes inputs `render()` set.** Angular sets those through input bindings, and a component with input bindings takes no other inputs. To change an input later, give `render()` its starting value.
- **`componentRef.setInput()` fails after `render()` sets inputs**, for the same reason (NG0317). Use `rerender({ inputs })`.

**Plain Vitest can't set signal inputs.** `ng test` compiles components ahead of time, so `inputs`, `rerender({ inputs })` and `componentRef.setInput()` all reach `input()` and `model()`. Plain Vitest compiles components at runtime, where Angular sees only `@Input()` and `inputs` metadata. Set a writable signal on `componentRef.instance` there instead.
