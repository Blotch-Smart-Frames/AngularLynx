# Build your app

`ng build` compiles your app into a [**bundle**](/guide/glossary#bundle), the single file a Lynx app runs from. This page covers what the build produces, production and development builds, environment files, size budgets and customizing the build tool.

To turn the bundle into apps you can install, see [Run on iOS and Android](/guide/native-apps).

## Build the bundle

```bash
ng build
```

The build writes its output to `dist/`, or to the build target's `outputPath` if you set one:

```bash
dist/
├── main.lynx.bundle
├── main.web.bundle
└── static/
    ├── image/
    │   └── logo.bf916cea19.png
    └── font/
        └── Inter-Regular.275384a067.ttf
```

| File               | What it is                                                                                     |
| ------------------ | ---------------------------------------------------------------------------------------------- |
| `main.lynx.bundle` | Your whole app: compiled code, templates and styles. iOS and Android run this file             |
| `main.web.bundle`  | The same app for the [web preview](/guide/glossary#web-preview)                                |
| `static/`          | Images, fonts, SVGs and media your code imports. Small files are put inside the bundle instead |

A bundle is like the JavaScript and CSS of a web app packed into one file. It doesn't run on its own: a [host app](/guide/glossary#host-app) with the Lynx engine loads it. See [How a Lynx app runs](/guide/concepts/how-it-runs).

`ng build` runs the `@blotch/angular-lynx-build:application` builder. It bundles with [RSpeedy](/guide/glossary#rspeedy), Lynx's build tool, and takes the entry point from the build target's `browser` option, as in any Angular app.

## Production and development builds

`ng build` makes a **production build**: minified, with Angular's dev mode off, and AngularLynx's debugging and profiling code removed.

As in Angular, the `optimization` option decides which kind of build you get. There's no separate mode option:

- `ng build` uses the build target's `defaultConfiguration`, which is `production` after `ng add`.
- `ng build -c development` uses `ng new`'s development configuration (`"optimization": false`), with dev mode on.
- Flags override single options, e.g. `ng build --source-map`.
- `ng serve -c production` serves a production build.

Some tools only work in development builds, such as [`LynxLogger`](/guide/debugging#stream-logs-to-your-computer) and the [render counters](/guide/profiling#watch-render-counters).

## Environment files

As in a web app, a configuration can swap one file for another with `fileReplacements`. That's how each build picks its environment, such as the backend it talks to:

```json title="angular.json"
"configurations": {
  "production": {
    "fileReplacements": [
      {
        "replace": "src/environments/environment.ts",
        "with": "src/environments/environment.prod.ts"
      }
    ]
  }
}
```

- **Everything the build makes gets the replacing file:** the code of both [threads](/guide/concepts/threads), the web preview and the apps `ng build --platform` makes. `ng serve` rebuilds when you edit it.
- **Paths are relative to the workspace,** like every path in `angular.json`, and can lead out of it, e.g. `../shared/environment.prod.ts`.
- **`ng generate environments`** creates `src/environments/` and a replacement for the development configuration. It warns that the build target uses a third-party builder; the replacement works.

## Rebuild on every change

```bash
ng build --watch
```

This rebuilds the bundle whenever a file changes, like the `npm run watch` script that `ng new` adds. It can't be combined with `--platform`. While developing, use `ng serve` instead.

## Lazy code ships in the bundle

Lazy routes (`loadComponent()`) and `@defer` blocks work as written. Their code is built into `main.lynx.bundle`, though, not into separate files.

So lazy loading doesn't make the bundle smaller. It still delays creating the views until they're needed. See [Routing](/guide/routing) and [`@defer`](/guide/defer).

## Budgets

**Budgets** fail the build when it grows past a size you set. They work as in a web app, with the same units and messages: over the warning size the build prints a warning, and over the error size it fails.

```json title="angular.json"
"configurations": {
  "production": {
    "budgets": [
      { "type": "initial", "maximumWarning": "2MB", "maximumError": "5MB" },
      { "type": "anyComponentStyle", "maximumWarning": "4kB", "maximumError": "8kB" }
    ]
  }
}
```

- **`initial`** checks each entry's Lynx bundle. **`anyComponentStyle`** checks each component's stylesheet.
- **The web preview bundle isn't checked.**
- **Why 2 MB?** `ng add` raises `ng new`'s `initial` budget from 500 kB and 1 MB to 2 MB and 5 MB. A Lynx bundle holds Angular twice, once for each of [Lynx's two threads](/guide/concepts/threads), so a new app's bundle is already about 1 MB.

The [build plugin's README](https://github.com/Blotch-Smart-Frames/AngularLynx/tree/master/packages/rsbuild-plugin-angular-lynx#budgets) explains what every budget type measures.

## Customize RSpeedy

An app doesn't need a `lynx.config.ts`. Add one to change something RSpeedy does, such as its environments, its entries or the AngularLynx plugin's options. Whatever it doesn't set still comes from `angular.json`.

Import `defineConfig` and the plugin from `@blotch/angular-lynx-build`, which brings RSpeedy with it:

```typescript title="lynx.config.ts"
import { defineConfig, pluginAngularLynx } from '@blotch/angular-lynx-build';

export default defineConfig({
  plugins: [pluginAngularLynx({ enableCSSInheritance: true })],
});
```

- **The plugin's options** are listed in the [build API reference](/api/build/).
- **RSpeedy's own options,** such as `output.assetPrefix`, are in [RSpeedy's docs](https://lynxjs.org/rspeedy/).
- **Another config file?** Point the build target's `config` option at it.
